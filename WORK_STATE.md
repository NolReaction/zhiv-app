# Рабочее состояние — административное дополнение к 0.7.0

14 октября 2026 пользователь попросил добавить обновлённую админку из `work/admin-operations` одним новым коммитом в `master` и разрешил пропустить полный прогон проверок. Основа — выпущенный `master` `691c41dc63939a73743ceb03ee09b59ce5f48bda`; административный источник — `d56dd36` из ветки с вершиной `36b9cb58ec1faa4dd9abd5d835ee1c61122353ce`. Историческая основа административной ветки не заменяет текущую 0.7.0.

## Состав

- Добавлены экраны «Выдать» и «Промокоды», административные выдачи валюты/предметов/улучшений, понятный аудит, управление наградами и сроками промокодов; подключены клиентские и Ktor/JDBC контракты.
- Уведомления, свет, редактор, вода, деревья и разговоры 0.7.0 сохраняются. Версии web/API и опубликованная новость остаются 0.7.0.
- V1–V50 текущего master сохранены побайтно; административные SQL перенесены без изменения содержимого в V51/V52. Конфликты документации, CI, upgrade/reset и dashboard объединены с текущими изменениями.
- Для серверов с уже применёнными старыми admin V50/V51 подготовлен узкий переход истории Flyway: только известные успешные SQL со сверенными checksum, изменение номера/имени записи без изменения игровых данных, безопасное продолжение прерванного перехода. Он выполняется отдельным migration entrypoint после штатной резервной копии и остановки API; runtime API историю не меняет.

## Проверки и публикация

Полный npm test, сборки VPS/Sites, API/PostgreSQL и ожидание CI для этого дополнения пропущены по явному разрешению пользователя. Результаты проверок исходной ветки и выпуска 0.7.0 относятся к своим коммитам. Пройдены быстрые typecheck, lint, architecture, security и diff-check. Подтверждены неизменность версии/новостей/мира/V1–V50, точные CRC административных SQL, уникальность V1–V52 и структура CI; код совместимости отдельно просмотрен. Шесть добавленных сценариев совместимости схемы включены в обязательный CI PostgreSQL, но локально не выполнялись.

Дополнение оформлено одним обычным коммитом с единственным родителем текущего master; исходные ветки и история сохраняются. Развёртывание действующего VPS выполняет пользователь через `scripts/deploy-update.sh`: отдельная чистая deploy-ветка от точного нового SHA, проверенная резервная копия, миграции, запуск web/API и readiness. Содержимое серверной БД и фактический запущенный SHA в этой сессии не читались; никаких выдач игрокам или сбросов данных не выполнялось.
