# Состояние работы

Рабочая ветка: `work/0.6.7`. Этап: восстановление сети и диагностика запуска, 2026-10-01. Версия приложения остаётся 0.6.6 до выпуска 0.6.7.

## Что реализовано

- На скриншотах с master загрузка профиля несколько раз показывала «Сервер молчит», затем восстановилась; в админке событий не было. Подтверждены недостатки кода, но причина конкретного сбоя устройства не установлена: серверные логи/соединение девушки не исследовались.
- Единый контроллер начального GET `/me`: до двух повторов через 1/3 с после временного отказа, учёт `Retry-After`, восстановление на online/pageshow/focus/возврате видимости. Один запрос одновременно; отмена при скрытии/уходе и защита от устаревших ответов. 401 ведёт к входу, постоянные 4xx не повторяются автоматически. Создание аккаунта и другие записи не переигрываются.
- Основной API и авторизация используют `request-deadline.ts`: внешний AbortSignal не отменяет таймаут, срок включает чтение JSON; нативный AbortSignal.timeout не требуется. Сохраняются причина отмены, Retry-After и безопасный request ID при некорректном ответе.
- Стартовые ошибки накапливаются в памяти страницы и отправляются после подтверждения владельца. 401/потеря сессии очищает этот буфер. До успешного `/me` полная перезагрузка/закрытие страницы теряет отчёт; неизвестному аккаунту события не приписываются.
- Клиентская диагностика распознаёт TimeoutError, нормализует два серверных кода, фильтрует сохранённые поля и имеет ограниченный fallback при недоступном storage. Явный 400 INVALID_INCIDENT удаляет только плохую запись, не блокируя остальные. Сеть/401/403 сохраняют очередь; повтор во время отправки не теряется. В отчёты не попадают URL, cookie, токены и тела ответов.
- Обновлены `docs/development/app-features.md` и `docs/operations/admin-panel.md`. Backend, БД, master и VPS не изменялись; исправления появятся у пользователей после отдельного выпуска/деплоя.
