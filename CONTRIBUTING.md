# Как работать с проектом

Начните с [путеводителя](docs/repository-guide.md). Новая огороженная поляна развивается в `feature/mochlik-grid-world`, созданной от `master` 0.6.1. Прежний открытый мир остаётся в `feature/mochlik-world`. В `master` попадает отдельно проверенный релиз.

## Небольшое изменение

1. Обновите рабочую ветку: `git pull --ff-only origin feature/mochlik-grid-world`.
2. Запустите `npm run dev:local`. Для телефона в той же сети — `npm run dev:lan`.
3. Найдите нужный раздел в `features/`. Компонент и его `.module.css` лежат рядом.
4. Измените одну законченную вещь. Проверьте её на узком и широком экране; для графики также проверьте день и ночь.
5. Перед коммитом выполните `npm run typecheck` и подходящие тесты. Перед релизом нужны обе сборки, полный набор веб-тестов и CI API.
6. Посмотрите `git diff --stat` и `git diff`: в коммит должны попасть только относящиеся к задаче файлы. Сохраните изменение обычным новым коммитом.

## Картинки и стили

- Иконки достижений: `public/achievements/`. Все шесть — SVG. Серый вид до получения задаёт CSS, отдельная чёрно-белая копия не нужна.
- Карты, детали зданий и маршруты: `public/world/`. [Описание файлов и ограничений](public/world/README.md).
- Рисунок Мохлика: `features/mochlik/pixel-sprite.ts`. Это программный пиксельный спрайт; его движения задаются отдельно.
- Новое изображение добавляйте в папку его назначения и регистрируйте в `features/world/art.ts`. Концепты и запросы для генерации — в `docs/game/concepts/`.
- Совпадение размера файлов недостаточно: у уровней дома должны совпадать точка опоры, вход, масштаб пикселя и освещение.

## Правила порядка

- Новый игровой компонент и его стиль кладите в соответствующий раздел `features/`. Общие элементы — в `components/`, общие функции — в `lib/`.
- Внутри раздела используйте `./file`; между разделами — `@/features/...` или `@/lib/...`.
- В `public/` лежат только используемые приложением файлы и их краткие описания. Удаляя ассет, проверяйте и динамические пути: имя файла может собираться из выбранного маршрута или ID достижения.
- История версий хранится в Git. Не добавляйте ZIP-копии проекта, `node_modules`, сборки и файлы `final-v2-copy`.
- Инструкции эксплуатации — `docs/operations/`, игра — `docs/game/`, релизы — `docs/releases/`, прежние решения — `docs/history/`.
- Секреты и реальные пользовательские данные не попадают в Git. Существующие миграции БД не переписывайте: изменение схемы оформляется следующей миграцией.
- Библиотечные `components/ui/`, конфигурацию сборки и скрипты деплоя меняйте по конкретной необходимости. Локальный API и настоящий Ktor должны одинаково понимать игровые команды.
