# Подготовка 0.6.7

**Рабочий документ, не опубликованный релиз.** Ветка `work/0.6.7-building-levels` развивается поверх `master` 0.6.6 (`97c11e0`). Версии кандидата web/API и новости подготовлены для 0.6.7. Подготовка, успешная локальная проверка или отправка коммита не означают перенос в `master` и развёртывание Selectel. Выполненные проверки конкретного этапа — в [WORK_STATE.md](../../WORK_STATE.md) и CI соответствующего SHA.

[Проверка безопасности 2026-10-06](../operations/security-review-2026-10-06.md) описывает проверенный ввод, поиск секретов, найденные ограничения и исправления. Это аудит доступных исходников и инструментов, не подтверждение защищённости запущенного сервера.

Эта страница описывает итоговое поведение ветки. Промежуточные тарифы, составы лавки и ранее отменённые механики здесь не дублируются; история этапов остаётся в Git и датированных исследованиях.

## Границы выпуска

- Отдельные рисунки есть не для каждого экономического уровня; используется ближайший доступный авторский вариант. Маяк и мост имеют варианты в редакторе, но игровое восстановление, проход по мосту и интерьер шахты ещё не выпущены. Домик Шишколапа подключён к карте и его циклу сна.
- Платежи, платный торговец реликвиями, пруд и посещение полянки друга — будущие механики. Их нельзя обещать как содержимое этой версии.
- Прежние поездки разрешено закончить, но новые старты прежнего контура закрыты. Совместимость данных и старого рендера сохраняется; она не является мусором для удаления.
- Ориентир около года до дома 5 не является результатом текущего расчёта с усиленными подарками. [Сценарии с полными подарками и местами](../game/production-slots-progression.md#актуальные-полные-подарки-сравнение-до-и-после) дают другие сроки при заданной стратегии. Они не учитывают весь рынок, будущую игру и поведение реальных игроков. [Ранний путь игрока](player-journey-0.6.7.md) помечен историческим, его числа не смешиваются с новыми.

## Дополнительный проход этого кандидата

- Поиск: «как», «стро», «ягод», «рыблка», несколько слов, неизвестный запрос, очистка и переход к действию на 320/390px и клавиатурой.
- Сеть: отключение до и после отправки покупки, потерянный ответ, перезагрузка с неопределённой командой, повтор подключения, возврат вкладки и смена аккаунта. Один requestId не создаёт два списания; до сверки действия заблокированы.
- AFK: ровно 5 минут без пользовательского ввода, фоновые heartbeat/анимации не продлевают активность, явное возвращение; оплаченная работа завершается в исходный срок. Две вкладки не удваивают время. Проверить переход UTC полуночи, границу 20 часов и серверный отказ старому presence ID.
- Заказы: дом 1–5, неполные производственные цепочки, снасти для акулы, старые карточки после улучшения; реальные списания и награда совпадают с карточкой.
- Админка: пустой период, фильтр игрока, операции еды/доски, суточное время, сигнал >20 часов, переход в журнал и отказ без административных прав.

Web и API обновляются согласованно. Новые поля заданий и мест производства читаются с совместимыми значениями по умолчанию; начатые заказы сохраняют свой результат и сроки. Нормальное обновление не требует сброса пользователей, БД или localStorage. После V32/V40/V41 возврат старого приложения не отменяет преобразование данных.

[`JdbcReleaseUpgradeIntegrationTest`](../../apps/api/src/test/kotlin/ru/zhiv/db/JdbcReleaseUpgradeIntegrationTest.kt) проверяет обновление заполненных V28, V30 и V44 до V45: сохранность аккаунтов, балансов, заданий, обращений, прежних квитанций и повторный запуск миграций. Отдельные JDBC-наборы проверяют экономику, рынок, обмен, награды, гостевые профили, номинал валют и активные игровые сеансы. Наличие теста не означает его успешное выполнение; нужна проверка итогового SHA с PostgreSQL.

## Проверки кандидата

Из чистого checkout выбранного SHA после установки зависимостей, последовательно:

```bash
npm run security:check
npm run security:history
npm run world:check
npm run typecheck
npm run lint
npm run economy:check
node scripts/audit-food-economy.mjs
npm test
npm run build:vps
```

`npm test` собирает Sites и запускает веб-тесты. Сборки и тесты, читающие `dist/`, не запускаются параллельно. `world:check` не должен изменять карту. При изменении исходников изображений отдельно проверяется [экспорт ассетов](../../art/README.md).

Для того же SHA нужны **Repository secret scan**, **Web checks**, **Ktor and PostgreSQL checks**, **Production Compose smoke test** из [CI](../../.github/workflows/ci.yml). JVM-проверки требуют JDK 25 и Docker; пропущенные Testcontainers-наборы не подтверждают сервер. Compose проверяет реальные маршруты, авторизацию, память, административный доступ, мониторинг, техработы, закрытие DEV и восстановление тестового backup. По договорённости рабочий коммит можно отправить, не дожидаясь CI; перенос в master всё равно требует результата этих проверок.

Дополнительный локальный HTTP-прогон: остановить `dev:local`, затем выполнить `node scripts/smoke-player.mjs`. Он сам запускает изолированный DEV-процесс на loopback, создаёт тестового игрока и проверяет старт, повтор команды, устаревшую ревизию и запрет ранней выдачи. Это не браузерное прохождение и не Ktor/PostgreSQL.

Ручной проход кандидата:

1. Новый игрок и аккаунт после 0.6.6: вход, отметки, календарь, люди, восстановление, игровые тапы, сохранённый гардероб/находки, первый подарок и первая стройка.
2. Телефон 320/390 px и широкий экран: круг/карта, скролл окон, клавиатура, фокус после закрытия, день/ночь/дождь, reduced motion. Проверить реальные сенсорные жесты и плавность на устройстве, а не только SSR/Canvas-стенд.
3. Мир: дома 1–5, сбор ягод и занятая кладовая, рыбалка и отмена на разных фазах, добыча с входом в шахту, разговор во время нового задания. При шахте 0 все горные маршруты закрыты; после получения первой стройки доступны пещера и камень. Поход и улучшение шахты взаимоисключаются до получения результата. Сохранённая прежняя пещерная вылазка при шахте 0 сохраняет награды/отмену, но не показывает героя и кирки в руинах. Переключить вкладки и перезайти во время стройки; жители не должны телепортироваться или перекрывать проход.
4. Хозяйство: одновременные производственные места, запрет второй стройки/двойного занятия Мохлика, готовый заказ до получения, меняющаяся цена при открытом подтверждении, истечение таймера и повтор после потерянного ответа. Не должно быть двойных списаний/наград.
5. Торговля: полная кладовая и резерв, видимый товар у Плёски, обязательная замена при обновлении, легендарные снасти, неизменная витрина рынка до срока, лимиты оборота, комиссия, возврат старого лота. Старый клиент или модифицированное тело запроса не обходят серверные правила.
6. Два устройства: передача управления, скрытая вкладка, потеря сети и возвращение старого владельца. Смена аккаунта очищает чужую память, реплики, гостевой и административный снимки.
7. Админка и приватность: отказ без прав, поиск/пагинация, снимок хозяйства без создания профиля, понятное устаревание при сетевой ошибке, очищение при отзыве доступа. Гостевой профиль не раскрывает закрытое хозяйство.

## Перед переносом в master

Приоритет завершающего этапа — проверка действующих игровых циклов:

- Пройти пустой старт до первой шахты без DEV, рынка и подарков; затем проверить работу → получение/отмена → повторный вход и смена вкладки для всех занятий и стройки. Следующая цель и причина блокировки должны быть понятны на телефоне.
- Проверить отдельную ветку кладовой 1–10 без требований к дому или другим зданиям: первые три уровня обычные, 4–10 требуют все три реликвии; всего 38 ядер, 12 кристаллов и 12 смолы. Старая оплаченная стройка 4/5 завершается без пересчёта, резерв торговли продолжает занимать место. [Расчёт реликвий](../game/rewards-and-relics.md#десять-уровней-кладовой) отделён от календарного прохождения; прежние прогнозы до переработки кладовой исторические.
- Проверить действующую доску из трёх заказов: выплаты монет, новые доступные ресурсы, рост партий и наград на домах 1–5, полные производственные цепочки, бесплатные и платные замены. Уже выданные условия сохраняются до смены карточки; новые учитывают завершённые улучшения и доступные снасти. Репутация и косметика за заказы остаются предложением будущего этапа.

Открыты до подтверждения на выбранном SHA: серверный CI/Compose с V45, ручной мобильный проход, проверяемый backup и согласованный состав выпуска. Исторические зелёные прогоны и результаты другой ветки не закрывают эти пункты.

1. Зафиксировать итоговый состав и результаты текущего SHA в WORK_STATE и CI. Проверить, что коммит содержит только нужные изменения, без временных изображений, секретов и пользовательских данных.
2. Сверить уже подготовленные версии 0.6.7 в `package.json`, `package-lock.json` и `apps/api/build.gradle.kts`, а также запись в `public/updates.json`. Перед публикацией проверить дату и состав новости по [порядку публикации](../development/updates-and-levels.md). Перенос в `master` — отдельный согласованный шаг; проверить CI итогового релизного SHA.
3. Получить этот SHA на сервере и следовать [обновлению клиента](../operations/client-updates.md). `scripts/deploy-update.sh` делает backup и включает техработы; скрипты сброса для обновления не нужны.
4. После обновления проверить readiness, ID сборки, основные функции и перенесённые данные. При ошибке следовать [эксплуатационной инструкции](../operations/operations.md); откат Git сам по себе не откатывает SQL и номинал валют.

Перед релизом сохраняются обе сборки, миграции, тесты и эксплуатационные инструменты. Полное переписывание навигации, разделение крупных координаторов или удаление старого рендера требует отдельной задачи и доказанной совместимости.
