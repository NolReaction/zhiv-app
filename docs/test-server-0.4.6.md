# Тестовый сервер 0.4.6

Пока сервер не арендован, эти команды — инструкция. Не запускать миграции против чужой/production базы без отдельного подтверждения и резервной копии.

## Состав

Caddy (единственные внешние порты 80/443) → web / API → PostgreSQL 18 в закрытой сети.

Порядок старта: db healthy → provision → migrate → API healthy → web → Caddy.

- `zhiv`: администратор только для первоначального provision и обслуживания.
- `zhiv_migrator`: владелец схемы, только одноразовый migration job.
- `zhiv_app`: runtime DML, без superuser/CREATE ROLE/CREATE DATABASE/владения схемой и без доступа к Flyway/старым таблицам восстановления.
- Flyway работает отдельным процессом; приложение само не меняет схему.
- V10 добавляет статус, V11 — единые настройки получателя, V12 — коды. Исторические миграции не переписываются.

## Новый сервер (Linux)

1. Установить Docker с Compose v2 и настроить DNS домена на сервер.
2. Скопировать `deploy/.env.example` в `deploy/.env`, задать DOMAIN.
3. Выполнить `node scripts/create-deploy-secrets.mjs`. Скрипт не перезаписывает существующие пароли. Каталог секретов — 700; файлы — 444, чтобы non-root процессы могли читать адресно смонтированные Compose secrets. Не делайте сам каталог общедоступным.
4. `docker compose --env-file deploy/.env -f deploy/compose.yml config --quiet`
5. `docker compose --env-file deploy/.env -f deploy/compose.yml up --build --detach --wait --wait-timeout 240`
6. Проверить HTTPS /healthz, /readyz и страницу; создать два тестовых профиля и проверить переключение доступа/статусы/восстановление.
7. Проверить, что снаружи закрыты 5432, 8080, 3000 и Caddy admin 2019; открыть SSH только администратору.

Не включать ENABLE_DEV_API на сервере. Не использовать localhost/LAN в публичных приглашениях. Файлы секретов исключены из git и Docker build context. Нельзя менять DOMAIN после установки PWA без плана переноса сессий.

## Обновление существующей базы

Сначала резервная копия и пробное восстановление. В db_admin должен быть **существующий пароль** администратора `zhiv`: генерация нового файла не меняет пароль уже созданного PostgreSQL volume.

На время provision/migrate остановить старые API/web. Provision переносит владение только объектами приложения в схеме public и базой zhiv; системные и другие базы не затрагивает. Новые пароли migrator/app нужны отдельные.

Перед каждой версией проверять, что новые миграции совместимы с данными, и повторять восстановление копии на изолированной БД. Не использовать `down --volumes` на рабочем сервере.

## Резервные копии и возврат

`pg_dump --format=custom` с административной учётной записью; хранить зашифрованную копию отдельно от сервера, регулярно проверять восстановление с `pg_restore --no-owner --no-acl` на изолированной базе, затем запускать provision/migrate.

Не копировать живой каталог PostgreSQL как обычные файлы. Откат к старому коду не является откатом схемы. Для полного возврата восстановить проверенную резервную копию в отдельную БД и переключить трафик в окно обслуживания.

## Перед внешним тестированием

- CI: Web, Ktor/PostgreSQL, production Compose smoke — все зелёные.
- HTTPS доверенный сертификат, постоянный домен, firewall, резервная копия и restore-drill.
- У каждого тестировщика сохранён личный код; восстановление закрывает его старые сессии.
- Ручной тест на настоящем iPhone/PWA обязателен: браузерная проверка на сервере его не заменяет.
