# Я живой / Мохлик — обзор проекта

**Автор: Дмитрий Сломов ([NolReaction](https://github.com/NolReaction)).** Приложение объединяет отметку «со мной всё хорошо» для близких и лесной игровой мир. Проект развивается от PWA к установленному клиенту iOS/Android с общей серверной моделью аккаунта и прогресса.

[Презентация и PWA](https://im-alive.ru/site) · [Приложение](https://im-alive.ru/) · [Быстрый запуск](../README.md#локальный-запуск) · [Мобильная сборка](development/native-mobile.md) · [Карта исходников](repository-guide.md).

## Роль автора и подход

Работа над проектом включает продуктовую концепцию, устройство общего клиента, Kotlin API и схему данных, правила игрового мира, нативные интеграции, автоматические проверки и эксплуатацию VPS. Разработка ведётся с использованием ИИ-инструментов. Инженерные решения и их ограничения можно проследить по исходникам, тестам и тематической документации ниже.

Основной результат — связанный продукт: действие в мобильном клиенте проходит через тот же API и изменяет тот же подтверждённый прогресс, который виден в вебе. Для установленного клиента отдельно решаются вход, сохранение незавершённых действий, доступ к возможностям телефона и обновление пакета приложения.

## Инженерные задачи

### Сохранение действий при нестабильной сети

Экономические команды содержат `requestId` и ожидаемую ревизию. Сервер проверяет условия и сохраняет результат; повтор использует исходный идентификатор. Мобильный клиент записывает поддерживаемые незавершённые действия и квитанции в SQLite до отправки, затем восстанавливает их после перезапуска. Такой порядок помогает разбирать неопределённый результат запроса без повторной выдачи награды.

[Активности и потеря связи](game/activity-and-offline.md) · [SQLite-журналы](../apps/mobile/src/native-storage/README.md) · [Архитектура](architecture.md).

### Владение данными и смена аккаунта

Мобильный вход использует системный браузер, одноразовый код, S256 PKCE и `state`. Секрет сеанса хранится нативно и не возвращается JavaScript. Записи и асинхронные ответы проверяются по владельцу и поколению сеанса: поздний ответ старого аккаунта не должен примениться к новому. Нативный HTTP ограничивает origin, перенаправления, время и размер ответа.

[Вход и границы доверия](development/native-mobile.md#вход-и-границы-доверия) · [iOS-модули](../apps/mobile/ios/App/App/) · [Android-модули](../apps/mobile/android/app/src/main/kotlin/ru/zhiv/mochlik/lab/).

### Общая игровая модель для клиентов

React-интерфейс, лесная сцена и игровые правила отображения используются вебом и установленным приложением. Каталог экономики читают TypeScript и Kotlin, а изменение кошелька, инвентаря и производств подтверждает сервер. Память визуальной полянки отделена от выдачи предметов и наград. Управление одной полянкой на нескольких устройствах согласуется через серверную аренду и явную передачу управления.

[Каталог экономики](../apps/api/src/main/resources/world/economy-catalog.json) · [Сохранение мира](game/forest-memory-sync.md) · [Организация кода](development/code-organization.md).

### Геопозиция с управлением доступом

Открытие карты после ранее выданного разрешения запускает частный поиск точки. Публикация координат зависит от выбора получателей и настроек пользователя; режимы OFF/«призрак», отзыв разрешения и смена аккаунта обрабатываются отдельно. Фоновый режим включается добровольно и не расширяет круг получателей. iOS использует Core Location, Android — службу переднего плана; ограничения ОС и принудительное закрытие учитываются в документации.

[Модель доступа](development/earth-sharing.md) · [Мобильная геопозиция](development/native-mobile.md#геопозиция-и-фон) · [Инвентаризация privacy](development/native-mobile-privacy.md).

### Воспроизводимый выпуск и обновление данных

CI собирает поддерживаемые клиенты, проверяет API с PostgreSQL, миграции и запуск production Compose. Процедура обновления управляет техработами, создаёт резервную копию и проверяет восстановление перед применением миграций. Наличие инструкции или зелёного CI не заменяет проверку фактического состояния публичного VPS.

[CI](../.github/workflows/ci.yml) · [Native CI](../.github/workflows/mobile.yml) · [Эксплуатация](operations/operations.md).

## Проверки и границы готовности

- **Общий CI:** TypeScript/ESLint, архитектурные границы, актуальность экспорта мира и отчётов экономики, обе веб-сборки, веб-тесты, Kotlin/PostgreSQL, миграции, Engine и production Compose.
- **Native CI:** мобильные JS-контракты, геометрия интерфейса, Android debug APK/lint/JUnit/merged manifest; iOS Simulator и сборка iPhone без подписи, исполняемые Swift-проверки.
- **Физические устройства:** звук, фон, батарея, разрешения и реальная доставка push проверяются по [матрице приёмки](development/native-mobile.md#проверки-и-приёмка). Подмена транспорта или звукового выхода в тесте не подтверждает реальную доставку/слышимость.
- **Статус каждого коммита:** [GitHub Actions](https://github.com/NolReaction/zhiv-app/actions). Число тестов и результаты прошлых сборок не используются как обещание результата нового коммита.

Веб/API имеют версию **0.7.2**, мобильный пакет — **0.3.2 / build 5**. Это разные версии компонентов одного продукта. Мобильная интеграция требует совместимого API со схемой **V84**: V83 добавляет мобильный вход, V84 — привязки APNs/FCM. Старые миграции сохраняются.

На текущем этапе распространение через TestFlight/магазины не настроено; Android CI выпускает debug APK, а release-подпись задаётся отдельно. Локальные игровые уведомления реализованы; APNs/FCM требуют ключей провайдеров, настройки подписанной сборки и проверки на телефоне. Обновление сайта не обновляет встроенный мобильный JavaScript — требуется новая установка пакета.

## Как посмотреть проект

1. Открыть [презентацию](https://im-alive.ru/site) и [веб-приложение](https://im-alive.ru/).
2. Запустить веб локально по [README](../README.md#локальный-запуск); для полноценного API и PostgreSQL использовать [инструкцию разработчика](development/local-development.md).
3. Собрать установленный клиент по [инструкции iOS/Android](development/native-mobile.md).
4. Найти интересующую подсистему в [карте файлов](repository-guide.md), затем прочитать её тематическую документацию и тесты.

Внешние ключи, подписи приложений и серверные секреты не являются частью публичного примера. Точные требования к окружению указаны в инструкциях запуска соответствующего компонента.
