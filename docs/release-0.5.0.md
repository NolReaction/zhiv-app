# 0.5.0 — вход в аккаунт, личные подписи и приватность

## Что изменилось

- Обычный вход через Telegram OIDC и одноразовый код на почту; привязка к существующему профилю и отдельные сессии браузеров. В профиле — способы входа и управление устройствами. Новый профиль создаётся только по явному выбору. Резервное восстановление остаётся аварийным действием с отзывом прежних сессий. [Настройка входа](auth-0.5.0.md).

- Нажатие на имя или аватар в «Людях» открывает карточку с исходным именем, ID и личной подписью. До 50 Unicode-символов; пробелы нормализуются, управляющие символы отклоняются. Пустое поле возвращает имя профиля. Подпись видна только автору, хранится на сервере отдельно от профиля человека и сохраняется после удаления и повторного добавления связи. Избранные остаются первыми, внутри разделов сортировка учитывает подпись.
- Результат игровой серии показывается внутри круга под «Я ЖИВОЙ»: `×5` или `Рекорд ×5`. Во время серии рядом остаются секунды и тонкая полоса. Надпись «Забег завершён» удалена. Ошибки сети и время последней отметки остаются отдельными сообщениями. Ежедневная серия и серверный интервал отметки не меняются.
- Копирование резервного кода использует видимое поле и синхронный fallback в том же нажатии, что и Clipboard API. Только подтверждённый Clipboard API показывает сообщение об успешном копировании. Legacy fallback предлагает проверить вставку; при отказе остаётся ручное выделение. Подтверждение сохранения и активация кода по-прежнему отдельные действия.
- Подсказки тумблера прямо говорят, что скрытие отметок действует и через общие группы. Подтверждение удаления связи объясняет, что общая группа может сохранить доступ. Удаление сохраняет ранее выбранные запреты; само по себе не превращается в блокировку человека.
- Лимиты авторизованных запросов привязаны к проверенному ID пользователя, а не только к общему IP. Разные сессии одного аккаунта имеют общий бюджет. Поддельные cookies не создают дополнительные бюджеты. Перед проверкой сессии действует общий предел IP. JDBC проверяет ID коротким индексным запросом, без пересчёта истории отметок.
- Анонимное восстановление получает отдельный IP-бюджет от активации резервного кода. Неструктурированный ответ 429 показывает понятное сообщение о частоте запросов.

## API и миграция

Добавлена **V14**, таблица `private_person_nicknames` с ключом `(viewer_user_id, subject_user_id)`.
Добавлена **V15**: привязанные способы входа и одноразовые запросы авторизации. Backend использует Nimbus JOSE JWT 10.9.1 и Angus Jakarta Mail 2.0.5. Старые миграции неизменны; runtime-права выдаёт существующий migrator.

`PATCH /api/v1/people/{circleId}/nickname`, JSON `{"nickname":"Мама"}`, требует действующую сессию, доверенный Origin и `Idempotency-Key`. Запись — идемпотентная установка значения; пустая строка удаляет подпись. Повторный запрос применяет переданное значение, как переключение избранного. Поле `nickname` в Person не входит в публичное имя пользователя.

Штатный порядок выпуска: миграции V14/V15 → новый API и web → проверки `/readyz`, входа, списка людей и сохранения подписи. Данные PostgreSQL и тома контейнеров сохраняются. Эта ветка сама по себе не обновляет действующий сервер.

## Проверка

Автотесты покрывают приватность подписи, сохранение после повторного добавления, очистку, запрет чужих/неавторизованных записей, сохранение OFF через группы после удаления, Unicode-валидацию, независимость лимитов разных пользователей на одном IP и невозможность обхода новым cookie. Backend-тесты также проверяют отозванные/просроченные сессии и удалённый профиль в короткой проверке ID.

Перед выпуском требуются TypeScript, ESLint, обе production-сборки, веб-тесты и backend/Compose CI с PostgreSQL. На реальном iPhone отдельно проверить вставку резервного кода в Safari и Telegram, ввод длинной подписи и расположение результата при узком экране. Автотест браузерного helper не доказывает работу системного буфера на конкретном телефоне.

## Проверка и включение провайдеров

Ветка проходит полный CI: веб, Ktor/PostgreSQL и production Compose. Итоговый статус смотрите в PR. Новые проверки включают подпись и claims Telegram ID token, одноразовый state, browser binding, email-коды, конфликты привязки, сохранение нескольких сессий и запрет отзыва чужой сессии.

Реальные ключи Telegram Login и настройки SMTP в репозиторий не входят. До их настройки соответствующие кнопки отключены; старые профили, сессии и резервное восстановление работают. На рабочем сервере необходимо применить миграции и обновить контейнеры из проверенного коммита. Эта ветка сама по себе сервер не обновляет.

Вход через Telegram и доставку писем нужно проверить с реальными настройками на iOS/Android/Safari/Chrome. Установка PWA остаётся возможностью браузера, а не условием использования приложения. Принудительное открытие другого браузера не требуется.
