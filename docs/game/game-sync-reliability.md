# Надёжность синхронизации игры

Исправления включены в релиз **0.6.1**. Применение к VPS требует обычного обновления API, миграции V26 и веб-клиента вместе. Подтверждённые очки и награды не пересчитываются.

## Что могло остановить игру

Предыдущий клиент мог отправлять пакет каждые 750 мс и дополнительно после каждого ответа в цикле. Лимит API составлял 4800 запросов **на аккаунт в час**: достаточно длительная игра исчерпывала его. Другое устройство и VPN не меняют этот ключ. Панель показывала только 5xx, поэтому 429 не выглядел как ошибка сервера. Это воспроизводимая причина в коде, а не подтверждение конкретного исторического инцидента: для него нужны журналы нужного времени.

Теперь пакет отправляется не чаще раза в две секунды после предыдущего подтверждения; пакет содержит до 60 тапов. Лимит запросов — 90 в минуту на аккаунт. `Retry-After` и увеличивающаяся задержка соблюдаются также после обновления страницы. Получение прогресса повторяется автоматически, с отдельным ограничением частоты.

## Очередь и единственный игрок

- API выдаёт разрешение на сбор тапов на 15 минут, до границы месяца UTC. Первый ещё неподтверждённый старт ограничен 60 тапами.
- Только одно разрешение может управлять живой игрой. После 30 секунд без отправки другое устройство может забрать управление; этот момент закрывает прежнее разрешение.
- До 30000 ожидающих тапов сохраняются в журнале браузера, отдельно для аккаунта. Это очередь доставки, а не источник подтверждённых очков. Очистка данных браузера удаляет локальную очередь.
- Очередь содержит время каждого тапа, исходную сессию и неизменяемый пакет с номером последовательности. Пакет записывается **до** сетевого запроса. При потере ответа повторяется тот же пакет.
- Тапы, собранные в пределах разрешения и до передачи управления, можно доставить в течение 24 часов. После истечения разрешения для новых тапов нужно подключение. Поздние/недопустимые тапы возвращаются отдельным числом и причиной; подтверждённые очки не отнимаются.
- Время событий ограничено разрешением; отдельный бюджет 30 тапов/с, всплеск 60, препятствует повторному фарму одного прошлого момента. Общий серверный бюджет доставки также 30/с. Его временное исчерпание не уничтожает пакет: ответ `GAME_PACING` не фиксирует новый sequence.
- Паузы серии определяются временем тапов, включая паузу внутри пакета. Задержка HTTP сама по себе серию не сбрасывает.
- Квитанции доступны не менее двух суток после истечения разрешения. Exact replay проверяется перед закрытием/истечением. Неизвестная или потерянная квитанция никогда не превращается в новый пакет другой сессии.
- При окончательном ответе `GAME_QUEUE_EXPIRED`, `GAME_SESSION_GONE` или `GAME_SESSION_CONFLICT` исходный пакет, его очередь и разрешение атомарно переносятся в `archivedQueues` того же локального журнала. Старые тапы не отправляются под новым разрешением и не объявляются отклонёнными: потерянное подтверждение могло уже увеличить серверный счётчик. Новую игру можно начать после успешной записи архива; счётчик непроверенных тапов виден в подробностях значка сервера. При ошибке записи исходная очередь остаётся активной. Лимит журнала — 2 МБ и 100 архивов, переполнение не удаляет старые записи.
- Две вкладки одного браузера координируют доступ к одному журналу; потерявшая владение вкладка не может перезаписать его. При недоступном/повреждённом хранилище новые игровые нажатия останавливаются, исходный журнал не затирается.

Браузерные временные отметки не доказывают, что нажимал человек. Эти ограничения убирают одновременное суммирование устройств и простой повтор старых событий; это не заявление о полном обнаружении ботов.

## Как разбирать инцидент

1. `/admin` → **Сервер** → выбрать 6 часов, 24 часа или 7 дней. Карточки состояния показывают текущие значения, графики — выбранный период. 5xx и ограничения 429 разделены. Исторические интервалы ошибок покрывают весь шаг графика, а не только последние две минуты каждого шага.
2. `/admin` → **Сбои у пользователей** → имя или публичный код игрока. Сравнить время события и время получения; устройство могло отправить журнал после возвращения связи.
3. Различать «Сообщение браузера» и «Ответ API». В записи есть операция, безопасный код, HTTP-статус, request ID, число ожидающих тапов и число объединённых повторов. Для поиска в прежних Docker logs использовать request ID и событие `api_failure`.
4. Новая таблица не содержит старые события задним числом. Если записи нет, это не доказательство отсутствия сбоя. Браузер может оставаться офлайн, а массовые повторы ограничиваются/объединяются.

События хранятся 30 дней с порционной очисткой. Авторизация определяется действующей серверной сессией; клиент не может назначить событие другому пользователю. Нет текстов исключений, cookie, токенов, резервных кодов, запросов SQL, URL с параметрами или произвольных стеков. При недоступной БД сохраняется диагностическая запись в серверном логе. Ограниченная запись инцидентов не должна превращать поток отклонённых запросов в неограниченную нагрузку на БД.

## Проверки

Web regression tests проверяют потерянный ACK, reload/offline, неизменяемую очередь, владение аккаунтом, backoff, часовые скачки, cutoff, event-time budget и восстановление открытия. PostgreSQL integration tests проверяют реальные ограничения миграции, позднюю доставку, replay после takeover, writer между соединениями и сохранение/авторизацию журнала.
