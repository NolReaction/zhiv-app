# Память Мохлика между устройствами

Снимок жизни полянки хранится в аккаунте: потребности, недавние занятия, безопасное положение или сон дома, рост грибов и состояние ягодного сада. Браузер выполняет Utility AI и анимации; сервер хранит подтверждённое состояние и разрешает запись одному клиенту. Постоянной серверной симуляции и пересчёта за время отсутствия нет.

Это отдельные данные от ресурсов, наград, инвентаря и путешествий. Сохранение памяти не выдаёт предметы и не меняет `world_profiles.revision`.

## Контракт

Все запросы требуют действующую сессию аккаунта. Запись дополнительно проверяет доверенный Origin. Ответы не кэшируются.

| Запрос | Назначение |
|---|---|
| `GET /api/v1/world/forest-memory` | Текущий снимок, его версия и состояние права записи |
| `POST /api/v1/world/forest-memory/commands`, `action: acquire` | Получить право записи; явный `takeover` передаёт его другому устройству |
| Тот же endpoint, `action: save` | Сохранить снимок с текущими `expectedRevision` и lease-токеном |
| Тот же endpoint, `action: release` | Освободить право записи |

Право записи — временная аренда на 90 секунд, привязанная к авторизованной сессии и `clientId`. Успешная запись продлевает её. При передаче аренды токен меняется: прежняя вкладка не может перезаписать новое состояние. Независимая `revision` защищает от устаревшей записи даже при совпадении времени на устройствах.

При переключении круг ↔ карта, разделов приложения или вкладок браузера сцена приостанавливается вместе с позициями, маршрутами и незавершёнными действиями всех трёх персонажей. Возврат не добавляет время отсутствия к анимации. Это краткоживущее состояние страницы, а не расширение серверного снимка.

Перед продолжением клиент заново проверяет право записи. Быстрая передача камеры может сохранить сцену при той же собственной действующей аренде. При более долгой паузе клиент сохраняет безопасный снимок и освобождает аренду; скрытая сцена не продлевает её и не опрашивает сервер. Продолжить прежнее движение можно только при точном совпадении ревизии собственного подтверждённого освобождения и успешном получении новой аренды без конкурирующей записи. Чтения самого снимка для этого недостаточно: проверяется также результат команды `acquire`. Чужой писатель, конфликт, ошибка сети или повторённая квитанция отменяют продолжение и требуют восстановления из серверного снимка.

После размонтирования последнего canvas сохраняется не более одной приостановленной сцены того же аккаунта и той же геометрии. Подключение другого аккаунта или другой карты вытесняет её. Выход из аккаунта, принудительный DEV-режим, очистка памяти, `pagehide` и настоящая перезагрузка не переносят старые маршруты. После перезагрузки остаётся только безопасное состояние из описанного ниже снимка.

Каждая команда имеет `requestId`. После потери ответа повторяется та же команда с тем же ID. Сервер хранит не более 64 квитанций на аккаунт; повтор не выполняет действие снова и не продлевает аренду. Нельзя автоматически повторять конфликт с новой версией поверх чужого снимка.

Клиент сохраняет состояние каждые 15 секунд активной сессии и пытается сохранить его при уходе в фон или закрытии сцены. Освобождение после сохранения выполняется в той же цепочке ответа, без нового таймера скрытой вкладки. Если получение аренды завершилось уже после размонтирования сцены, клиент освобождает её по полученному токену. Закрытие браузера всё равно не гарантирует доставку последнего запроса: останется последнее подтверждённое сохранение, а аренда истечёт через 90 секунд.

При подтверждённой чужой аренде в круге и на карте автоматически появляется центральное окно «Полянка на паузе» с действием «Продолжить здесь». Оно объясняет также случай оставшейся аренды предыдущего запуска; на карте можно вернуться на главный экран. Нажатие явно передаёт управление и загружает серверный снимок. Одно лишь истечение собственной аренды сначала вызывает проверку сервера и не показывает предупреждение о другом устройстве. Активный клиент без права записи проверяет обновления раз в 15 секунд. Отметки жизни и игровые клики имеют отдельный протокол.

Сначала клиент загружает серверный снимок. Пока запись принадлежит другому устройству, связь потеряна или снимок ещё загружается, декоративная симуляция на паузе. Локальный кэш помогает показать сохранённую полянку, но не перезаписывает существующую серверную память после восстановления связи. Если серверного снимка ещё нет, первое сохранение переносит текущее безопасное локальное состояние. При заблокированном localStorage серверная синхронизация продолжает работать.

### Версии снимка и сад

Новый клиент читает версии **1 и 2**, а сохраняет **2**. Версия 1 сохраняет прежний набор полей и занятий: `garden` в ней отсутствует, в том числе сервер не добавляет `garden: null`. Версия 2 требует `garden` и допускает занятия `water-bush` и `harvest-berries` в короткой памяти. Остальные правила потребностей, безопасной позиции и грибов сохраняются.

| Поле `garden` | Значение и ограничения |
|---|---|
| `bushes` | Не более 32 кустов с уникальными ID |
| `bushes[].id` | Стабильный ID из карты, 1–160 символов без управляющих символов |
| `bushes[].position` | Координаты размеченного входа к кусту; каждая координата — конечное число от 0 до 10 000 000 |
| `bushes[].growth` | Созревание ягод, 0–1 |
| `bushes[].moisture` | Влажность куста, 0–1 |
| `bushes[].waterIn` | Оставшееся время до повторного полива, 0–600 активных секунд |
| `basketBerries` | Уже доставленные в корзинку декоративные ягоды, целое число 0–12 |

В HTTP-контракте браузер, локальный API и Ktor отклоняют неизвестные поля, неверные типы, повторяющиеся ID и недопустимые значения. Лимиты остаются прежними: 32 768 байт UTF-8 на снимок и 65 536 байт на тело команды. Контракт находится в [`forest-memory-model.ts`](../../features/world/forest-memory-model.ts) и [`ForestMemory.kt`](../../apps/api/src/main/kotlin/ru/zhiv/forest/ForestMemory.kt).

Ключ localStorage намеренно остаётся `zhiv:forest-memory:v1:<account>`: цифра в ключе не обозначает версию лежащего внутри снимка. Старый кэш восстанавливается, сад создаётся из текущей карты, следующее сохранение обновляет тот же слот до v2. Чистить localStorage для этого не нужно; существующий серверный снимок по-прежнему имеет приоритет.

## Что восстанавливается

- Серверный снимок содержит только состояние Мохлика, грибов и сада. Координаты, потребности, улов и маршруты Плёски, а также положение и маршрут Шишколапа в него не входят. Экономический заказ строителя хранится отдельно: при новом входе уже существующий заказ размещает его у безопасной рабочей точки постройки, без повторной дороги из центра. Если таймер завершён, ёжик ждёт получения у здания. До первого подтверждённого снимка экономики и загрузки правильной геометрии его кадр скрыт; новый заказ после пустого начального снимка запускает обычный подход. Во время уже открытой сцены повторная hydration сохраняет валидную текущую точку ног строителя, но пересоздаёт его маршрут и сверяет заказ заново; изменение уровня здания не переносит его обратно к дому.
- Потребности и короткая память занятий/мест; промежуточные решения и DEV-журнал не переносятся.
- Только безопасная позиция на текущей карте либо проверенный сон в доме. При сохранении во время ходьбы запоминается проходимая точка ног, а не цель или весь путь. После настоящей перезагрузки AI выбирает занятие заново. Прыжок, незавершённый путь, положение лап и встреча с насекомым не возобновляются с произвольного кадра.
- Действующая вылазка берётся из подтверждённой экономики: при загрузке уже начатой рыбалки или работы в шахте сцена использует проверенное место этого занятия. Она не заставляет Мохлика повторять старый путь от дома и не меняет время завершения задания.
- При изменении геометрии fingerprint отменяет прежнюю позицию и пространственную историю. Потребности сохраняются; грибы сопоставляются по ID и координатам.
- В пределах той же карты кусты восстанавливают созревание, влажность и остаток задержки полива только при совпадении ID и координат входа. Перенесённый куст получает начальное состояние. Уже доставленные ягоды сохраняются при правке геометрии.
- Если после правки для корзинки временно нет безопасного места, количество ягод удерживается во внутреннем `unplacedBerries` и записывается в обычное `garden.basketBerries`. После восстановления доступного места и пересоздания сцены ягоды снова появляются в корзинке; отдельного поля `unplacedBerries` в API нет.
- Полив и сбор не возобновляются посреди анимации. Сбор меняет куст и количество ягод только при доставке корзинки: до этого момента перезагрузка или передача управления сохраняет исходный урожай. Корзинка возвращается в доступное место текущей карты, незавершённый перенос не повторяется.
- Отсутствие не расходует силы и не начисляет рост или награды. Погода, птицы и популяция насекомых не становятся синхронными между устройствами.

Формат и размеры снимка проверяются клиентом и сервером. Серверный JSON не является способом передавать произвольные данные, начислять валюту или менять карту. Принудительный DEV-сценарий сохраняет чистый снимок и отключает запись его дальнейших изменений до конца сессии; просмотр диагностики память не отключает.

## База и жизненный цикл аккаунта

Миграция **V31** добавляет две таблицы:

| Таблица | Содержимое |
|---|---|
| `forest_memory` | Один снимок на аккаунт, revision и аренда записи |
| `forest_memory_receipts` | Ограниченная история принятых команд для безопасных повторов |

Для снимка v2 **новая SQL-миграция не нужна**: V31 уже хранит снимок в JSONB без ограничения версии. Проверку содержимого выполняют согласованные клиентский и серверный контракты; существующие строки v1 читаются без изменения базы.

Удаление аккаунта удаляет обе записи. При объединении сохраняется память целевого аккаунта; если у него снимка нет, переносится память исходного. Аренда сбрасывается: старые устройства должны заново получить право записи. Восстановление доступа к тому же аккаунту сохраняет снимок, но отозванная сессия больше не может писать.

## Обновление сервера

Дополнительные секреты и ручной SQL не нужны. Из чистого checkout проверенного коммита, включающего web и API:

```bash
bash scripts/deploy-update.sh
```

Скрипт собирает образы, делает backup, включает техработы, останавливает прежние web/API и запускает Compose-сервис `migrate`. Flyway применит ещё не установленные миграции, включая V31 при первом внедрении памяти; уже применённая V31 повторно не запускается. Затем стартуют новые API/web и снимаются техработы. Если миграция не прошла, окно техработ остаётся до исправления. Порядок выпуска — [обновление клиента](../operations/client-updates.md).

Переход на v2 выпускается **совместно для API и web**: старый API не принимает новый снимок, а старый web не читает v2 после первого сохранения сада. При выпуске обновите версию/сборку согласно процедуре обновления клиента и обеспечьте перезагрузку открытых вкладок и PWA после техработ. Один лишь новый web поверх старого API несовместим. После появления v2 в базе старый API также не подходит для отката: нужна сборка, которая продолжает читать обе версии, без удаления памяти пользователей.

Проверить схему на VPS из корня проекта:

```bash
sudo docker compose --env-file deploy/.env -f deploy/compose.yml exec -T db \
  psql -X -U zhiv -d zhiv -v ON_ERROR_STOP=1 \
  -c "SELECT version, description, success FROM flyway_schema_history WHERE version = '31';"
curl -fsS --max-time 20 https://im-alive.ru/readyz
```

Сброс базы не является миграцией. `reset-user-data.sh` обновлён для схемы V31 и включает память Мохлика; применять его можно только для намеренного удаления всех пользователей.

## Проверка

В двух браузерах войдите в один аккаунт. Дождитесь подтверждённого сохранения в первом, затем откройте карту во втором. Проверьте получение снимка, явную передачу управления, отказ старому устройству в записи, перезагрузку, уход в фон и восстановление сети. По внешнему кадру нельзя требовать полного совпадения анимаций: переносится безопасное состояние, а не видеопоток.

Для сада дополнительно проверьте перенос влажности/задержки полива и доставленных ягод, перезагрузку при переносе корзинки, чтение старого v1 и сохранение ягод при временно недоступном месте корзинки. Принудительное созревание и занятия из DEV изолированы от памяти аккаунта. Правила самих занятий — [ягодный сад](clearing-garden.md).

В CI включены проверки контракта, аренды и конкуренции в PostgreSQL, обновления заполненной БД V30 → V31, runtime-прав через production Compose, восстановления аккаунта и полной очистки тестовых данных. Их фактический результат проверяйте для нужного коммита; локальные ограничения и выполненные проверки записаны в `WORK_STATE.md`. Подробности решений и текущий статус памяти доступны в DEV; сама панель не выдаёт право записи.
