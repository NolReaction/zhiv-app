# Устойчивость сервера и доставка тревог

Исходники: `deploy/monitoring/`, `scripts/check-deploy-perimeter.py`,
`scripts/check-alert-delivery.py`, `scripts/restore-backup-drill.py`.
Эти инструменты не меняют игровую экономику, права игроков или частоту их действий.
Фактическая конфигурация VPS проверяется отдельно: наличие файлов в Git не означает,
что внешний фильтр, уведомления или резервные копии уже включены.

## Проверка конфигурации без обращения к игре

Из корня репозитория на машине, где настроен Compose:

```bash
set -o pipefail
docker compose --env-file deploy/.env -f deploy/compose.yml config --format json |
  python3 scripts/check-deploy-perimeter.py
```

Проверка читает JSON из stdin, не запускает контейнеры и не отправляет запросов.
Она отклоняет опубликованные порты сервисов кроме Caddy, лишние порты Caddy,
host networking, privileged/cap_add, Docker socket и опасные host mounts;
проверяет внутреннюю backend-сеть и read-only root приложения/мониторинга.
Вывод содержит только фиксированные пояснения. Сам JSON может содержать секреты:
не используйте `tee`, не прикладывайте его к тикету и не запускайте с shell trace.

Это не сканер работающего VPS. После изменения инфраструктуры отдельно сверяют
фактические слушающие порты, host firewall и настройки провайдера. При подключении
CDN/L7-защиты закрывают обход через origin и проверяют, что только доверенная цепочка
прокси задаёт IP клиента. Нельзя просто доверить произвольному `X-Forwarded-For`
роль адреса для авторизации, лимитов или расследования. Проверка DNS/прокси и внешние
пробы требуют известного целевого окружения; этот скрипт их не выполняет.

## Внешние уведомления, отдельное включение

Обычная установка по-прежнему работает без Alertmanager. Дополнительный overlay
`deploy/monitoring/alerting.compose.yml` подключает внутренний Alertmanager и доставку
текущих тревог Prometheus в **совместимый с Alertmanager webhook**. Это не адрес
Telegram Bot API: получатель должен принимать JSON формата Alertmanager. Он выбирается
и настраивается владельцем отдельно. Скрипты не регистрируют сервис, не покупают тариф
и не посылают пробное сообщение.

1. Сначала настройте обычный monitoring по [инструкции админки](admin-panel.md).
2. Создайте `deploy/.secrets/alerts/` с правами 0755 под приватным
   `deploy/.secrets/` (0700). В файле `webhook_url` сохраните одну HTTPS-ссылку
   получателя; права файла — 0444 для чтения контейнером. Весь путь закрыт приватным
   родительским каталогом. Не храните ссылку в `.env`, Git, history или сообщениях.
   API не получает этот каталог: ему смонтирован только соседний `monitoring/`.
3. Выполните `python3 scripts/check-alert-delivery.py`. Проверяется формат и доступ;
   URL не выводится и никакое сообщение не отправляется.
4. После выбора получателя создайте пустой файл `deploy/.secrets/alerts/enabled`.
   Следующий **обычный согласованный деплой** через `scripts/deploy-update.sh`
   подключит overlay и сохранит его при дальнейших обновлениях. Само создание файлов
   ничего не запускает. Во время применения возможна доставка уже действующих тревог.

Перед включением можно проверить конфигурацию, не запуская отправитель:

```bash
docker compose --env-file deploy/.env -f deploy/compose.yml \
  -f deploy/monitoring/alerting.compose.yml --profile monitoring \
  run --rm --no-deps --entrypoint /bin/amtool alertmanager \
  check-config /etc/alertmanager/alertmanager.yml
docker compose --env-file deploy/.env -f deploy/compose.yml \
  -f deploy/monitoring/alerting.compose.yml --profile monitoring \
  run --rm --no-deps --entrypoint /bin/promtool prometheus \
  check config /etc/prometheus/prometheus.yml
```

У Alertmanager нет опубликованного порта, доступа к Docker socket, данным БД или
секретам входа. Он получает только собственный URL. HTTP redirects отключены.
Тревоги группируются, повтор отправляется через четыре часа; сообщения о восстановлении
включены. Здесь ограничивается повтор **тревог**, а не игровые запросы.
Объём/CPU/RAM отправителя нужно измерить на своём сервере, затем задать бюджет
в локальном Compose override. Произвольный жёсткий предел приложения здесь не вводится.

Перед включением техработ deploy проверяет обе конфигурации. После успешных проверок
API/web и версии сборки трафик открывается до обновления необязательного мониторинга.
Ошибка проверки/перезапуска сборщика или запуска отправителя даёт предупреждение
и не удерживает здоровую игру в техработах. В Prometheus появляются отдельные тревоги недоступности Alertmanager
и неудачной доставки. Они видны в источнике мониторинга, но **сломанный канал не может
надёжно уведомить о собственной поломке**. Нужна независимая внешняя проверка
доступности и фактическое получение согласованного тестового уведомления.
Одна успешная `check-config` ещё не подтверждает доставку.

Отключение: остановите только `alertmanager` с теми же двумя `-f`, удалите marker
`deploy/.secrets/alerts/enabled`, затем при очередном обновлении вернётся обычный
Prometheus. Не выполняйте общий `down -v`. Если нужно отключить маршрут немедленно,
пересоздайте только Prometheus с базовым Compose; приложение не нужно перезапускать.

## Нагрузка и восстановление

Сначала зафиксируйте обычный и пиковый RPS, p95, HTTP 5xx/429, использование RAM/CPU,
ожидание БД, число соединений и свободный диск. По отдельности проверяйте чтения,
экономические команды и диагностику. Высокая частота — сигнал для расследования,
а не доказательство злого умысла: её может создавать ошибка клиента или несколько вкладок.
Бюджеты контейнеров выбирайте по измеренному пику с запасом, проверяя восстановление
после отказа. Жёсткий лимит памяти без измерений может превратить нагрузку в OOM/restart.

Проверку копии запускайте на отдельной машине с локальным Docker и свободным диском,
используя **доверенный** PostgreSQL custom dump. SQL внутри чужого дампа может исполнять
команды; это не средство анализа неизвестных архивов.

```bash
python3 scripts/restore-backup-drill.py /secure/path/zhiv.dump
# Только план. Для реального восстановления в изолированный локальный проект:
python3 scripts/restore-backup-drill.py /secure/path/zhiv.dump --execute
```

Скрипт жёстко выбирает локальный `/var/run/docker.sock`, уникальное имя проекта,
`deploy/restore.compose.yml`, закрытую сеть и одноразовый диск. Он не принимает URL
БД, имя production project или внешний Docker context; переменные DOCKER/COMPOSE/PG
не переопределяют цель. Прямой доступ к локальному Docker должен быть настроен заранее.
Перед запуском проверяется также отрендеренный Compose: чужое имя тома, external volume,
дополнительный сервис или опасный mount не допускаются даже при изменении YAML.
По умолчанию контейнеры не создаются. `--execute` выполняет полный restore, читает
последнюю успешную миграцию и удаляет только свой проект/том даже после ошибки.
`--expect-schema 61` — пример проверки точной версии для соответствующей копии;
укажите версию проверяемого выпуска. Исходный архив не удаляется и не меняется.
Вывод не содержит строк игроков или секретов. При неудачной очистке выводится точное
имя оставшегося изолированного проекта; эту ошибку нельзя считать успешной проверкой.

Успешный restore подтверждает читаемость и восстановимость этой копии, но не всю
работоспособность приложения и не выполнение RPO/RTO. Для этого отдельно проверяют
срок копии, прикладные операции на стенде и фактическое время полного возврата сервиса.
Процедура внешнего резервирования описана в [эксплуатации](operations.md).

Проверки изменений: `node --test tests/operations-resilience.test.mjs
tests/deploy-lifecycle.test.mjs`. Они проверяют изоляцию, запрет утечки секретов,
ошибки восстановления и порядок деплоя через fake Docker, **не имитируют успешный
реальный PostgreSQL restore**. CI отдельно проверяет `amtool check-config` и
`promtool check config/rules` с `.invalid` получателем, не запуская отправитель.

Источники конфигурации: [Alertmanager](https://prometheus.io/docs/alerting/latest/configuration/),
[Prometheus](https://prometheus.io/docs/prometheus/latest/configuration/),
[Selectel: границы стандартной защиты](https://docs.selectel.ru/anti-ddos/ddos-selectel/).
Защита L3/L4 не заменяет фильтрацию корректных HTTP-запросов на L7.
