# Обновление открытого приложения и техработы

[Документация](../README.md) · [Эксплуатация](operations.md) · [Новости версий](../development/updates-and-levels.md)

Новости и доставка новой программы — отдельные механизмы. `public/updates.json` содержит тексты объявлений. `/app-status.json` сообщает о готовности сервера и идентификаторе сборки; по нему открытая PWA переходит на новую версию автоматически.

## Обычный выпуск на VPS

После проверки CI получите нужный коммит в чистый checkout сервера и выполните из корня:

```bash
bash scripts/deploy-update.sh
```

Скрипт:

1. Берёт блокировку от одновременных запусков, создаёт ID выпуска, собирает образы и проверяет конфигурацию Caddy. Приложение продолжает работать.
2. Публикует статус техработ, включает запрет внешних запросов и обновляет Caddy. `/app-status.json` остаётся доступен; остальные маршруты получают `503` с `Retry-After: 15`.
3. Останавливает прежние web/API с ожиданием завершения запросов. После остановки создаёт итоговый backup в `../zhiv-backups` и действительно восстанавливает его в отдельной временной PostgreSQL без открытых портов. Проверочный контейнер и его том удаляются; исходная база и архив сохраняются. До успешного восстановления миграции не запускаются.
4. Запускает миграции и новую версию (ожидание до 600 секунд). Проверяет readiness, доступность сервисов из Caddy и совпадение ID работающего web с этим выпуском.
5. Снимает ограничение и публикует готовность. Открытые клиенты получают её и перезагружаются.

Для проверки восстановления нужны Python 3, Docker и свободное место под временную копию базы. При ошибке backup или восстановления приложение остаётся на техработах, схема не меняется; исправьте причину и повторите запуск. Отдельные секреты или почтовые настройки не нужны. Скрипт использует прежний `deploy/.env`. Для первой установки остаётся [первичная настройка](server-setup.md); runtime-статус появится при первом обновлении.

ID сборки передаётся Docker явно через `--build-arg`: обычный `sudo` очищает переменные окружения. Запускать скрипт через `sudo -E` или ослаблять проверку совпадения ID не требуется.

**Первое внедрение:** вкладка со старым кодом, в котором ещё нет этого механизма, не умеет получать команду обновления. Игрок должен один раз открыть/перезагрузить приложение после установки этой версии. Дальнейшие обновления обрабатываются автоматически. Данные браузера очищать не нужно.

## Поведение клиента

- В JavaScript зашит ID **его собственной сборки**. Сравнение с первой полученной серверной версией не используется: старая вкладка должна распознать новую версию сразу.
- Статус запрашивается без кеша раз в 15 секунд в видимой вкладке, при возвращении в приложение и восстановлении связи. Service Worker не перехватывает этот запрос.
- `maintenance: true` показывает экран техработ. После готовности нового ID клиент показывает короткое уведомление, ещё раз проверяет сервер и перезагружает страницу.
- Перезагрузка сохраняет аккаунт, localStorage и очередь игровых запросов. Перед ней проверяется возможность сохранить локальные действия и черновик обращения. Если данные сохранить нельзя, автоматическая перезагрузка останавливается.
- Ошибка сети или некорректный статус сами по себе не означают техработы и не очищают данные. Скрытая/офлайн-вкладка ждёт возвращения.
- Отметка попытки в sessionStorage и параметр `_appBuild` в URL предотвращают бесконечный цикл при устаревшем ответе: показывается ручной повтор.
- В development принудительный переход по ID отключён, чтобы сборки и hot reload не перезагружали рабочую страницу.

Ожидание очередного опроса — до 15 секунд; принудительное обновление не является мгновенным push-уведомлением. Серверный запрет запросов работает независимо от того, успела ли конкретная вкладка показать экран.

Офлайн-кэш статических ресурсов соблюдает `no-cache`, `must-revalidate`, `no-store` и `private`, включая записи прежнего worker. Next static сохраняется только с `immutable`; изменяемые DEV-чанки не входят в shell. Производственный анонимный HTML shell остаётся доступен офлайн, приватные API — только через сеть. Для ошибки модулей в локальном DEV используйте [инструкцию восстановления](../development/local-development.md#ошибка-module-factory-is-not-available), не очищайте весь localStorage игрока.

## Если старая установка зависла после обновления

Откройте `/recover.html` в проблемном браузере или выберите «Восстановить запуск» на экране ошибки игры. Страница работает отдельно от игрового JS. По кнопке «Обновить файлы и открыть игру» она проверяет готовность сервера, удаляет только публичные кэши `zhiv-shell-*`, `zhiv-assets-v1`, `zhiv-meta-v1`, запрашивает обновление существующего service worker и открывает главную с новым параметром URL. Страница и её скрипт отдаются с `no-store` в Next и Sites.

Cookies входа, localStorage/sessionStorage, IndexedDB, игровые очереди, настройки и регистрация push не удаляются. Операция не очищает серверную БД и не запускает reset. При отсутствии сети или техработах очистка не начинается. Это способ исключить повреждённые или старые файлы, а не гарантия исправления любого зависания.

«Проверить соединение» выполняет только GET readyz/status/me/world/economy и показывает HTTP, базовую проверку JSON, код ошибки и request ID без содержимого профиля или ответов. HTTP 200 с верным базовым форматом не заменяет полную проверку игрового контракта. Если ошибка остаётся, сохраните этот результат и конкретный текст ошибки запуска; сверка теперь сообщает ошибку мира или хозяйства вместо одного общего сообщения.

На iOS установленная PWA может иметь отдельное хранилище: восстановление в Safari не очищает кэш другой среды. Для PWA используйте ссылку с её экрана ошибки. Не удаляйте PWA и все данные Safari как первый способ восстановления. Рабочий новый браузер также может использовать новый аккаунт: сравнивайте запуск того же аккаунта, не передавайте его cookies или коды входа для диагностики.

## Где менять

| Задача | Файл |
|---|---|
| Опрос, проверка статуса, повтор и защита от циклов | [app-lifecycle.ts](../../features/updates/app-lifecycle.ts) |
| Экран и кнопки | [app-lifecycle-view.tsx](../../features/updates/app-lifecycle-view.tsx), [CSS](../../features/updates/app-lifecycle.module.css) |
| Генерация одного ID для JS и публичного статуса | [app-build.mjs](../../scripts/app-build.mjs), команды `build` / `build:vps` в [package.json](../../package.json) |
| Порядок выпуска, бэкап, блокировка и обработка ошибок | [deploy-update.sh](../../scripts/deploy-update.sh) |
| Доступ к статусу во время остановки web/API и HTTP 503 | [Caddyfile](../../deploy/Caddyfile), [compose.yml](../../deploy/compose.yml) |
| ID внутри Docker-сборки | [web.Dockerfile](../../deploy/web.Dockerfile) |
| Исключение статуса из офлайн-кеша | [sw.js](../../public/sw.js) |
| Восстановление публичных файлов без игрового JS | [recover.html](../../public/recover.html), [recover.js](../../public/recover.js) |

Генерируемый `public/app-status.json` не редактируется вручную и не хранится в Git. Runtime-файлы VPS — `deploy/runtime/app-status.json`, `maintenance` и `deploy.lock`; Caddy читает каталог как `/srv/deploy`. В репозитории остаётся только `.gitkeep`.

Формат статуса: `{schemaVersion: 1, buildId: "уникальный-ID", maintenance: false, message?: "текст"}`. Не переиспользуйте ID для разных сборок. Обычные npm-команды создают его автоматически; `APP_BUILD_ID` позволяет задать его явно. Sites получает статус своей сборки, но шлюз техработ из этого документа относится к VPS/Caddy.

Обе локальные сборки используют общий `public/`. Если после сборки Next запущен `npm test` (сборка Sites), перед ручным `start:vps` снова выполните `build:vps`: публичный статус должен соответствовать запускаемому JavaScript. Docker-образ уже содержит согласованный комплект; обычный `dev:local` по ID не перезагружается.

## Если выпуск оборвался

При ошибке сборки или бэкапа рабочие сервисы не переключаются. При ошибке после включения техработ статус остаётся закрытым с сообщением о задержке. Посмотрите логи, исправьте причину и повторите тот же `deploy-update.sh`. Не удаляйте флаг вручную ради открытия недоступного или частично обновлённого приложения. Отмена скрипта не откатывает миграции; восстановление БД — отдельная операция по [инструкции](operations.md).

Если первый выпуск 0.6.5 остановился с `The running web build does not match this deployment`, получите исправленный коммит и снова выполните скрипт. В первоначальном скрипте `sudo` мог убрать ID из окружения сборки. Повторный запуск создаёт согласованный образ, проверяет его и сам снимает техработы; уже применённые миграции повторно не изменяют базу. Сбрасывать БД или восстанавливать бэкап из-за этого несовпадения не нужно.

Проверки: `tests/app-lifecycle.test.mjs`, `tests/deploy-lifecycle.test.mjs`, `tests/pwa-contract.test.mjs`; CI дополнительно проверяет реальный Caddy/Compose: статус остаётся HTTP 200, главная и запись в API получают 503.
