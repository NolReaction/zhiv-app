# Уведомления PWA

Настройки находятся в главном приложении: профиль → шестерёнка → «Уведомления». Звук вынесен в отдельный раздел. Сохранение параметров не запрашивает разрешение браузера. Подключение устройства происходит только после явного нажатия пользователя.

Если параметры уведомлений изменены, «Все настройки», другая вкладка профиля и основная навигация сначала показывают предупреждение. «Вернуться к настройкам», Escape, крестик и нажатие вне окна оставляют черновик; «Выйти без сохранения» возвращает сохранённые параметры и выполняет выбранный переход. Успешное сохранение снимает предупреждение, ошибка сохраняет черновик. Во время сохранения выход ждёт результата. При закрытии или перезагрузке страницы дополнительно используется стандартное предупреждение браузера, если он поддерживает `beforeunload`; на мобильной ОС этот механизм не гарантирован.

## Подключение устройства и повторная попытка

Разрешение браузера и подключённое устройство — разные состояния. «Подключены на этом устройстве» появляется после создания браузерной подписки и подтверждения API. Если разрешение уже получено, но регистрация не завершена, карточка предлагает «Завершить подключение». Этапы и ошибка показаны рядом с кнопкой, отдельно от сохранения предпочтений.

- **iPhone/iPad, включая заход из Safari или Яндекс Браузера:** нужна iOS/iPadOS 16.4+ и запуск приложения с экрана «Домой». Если в текущем браузере нет команды установки, откройте сайт в Safari → «Поделиться» → «На экран „Домой“», затем запустите с новой иконки. Обычная вкладка показывает эту инструкцию вместо кнопки подключения.
- **Яндекс Браузер на Android:** уведомления сайтов поддерживаются. При запрете: настройки браузера → «Уведомления» → «Уведомления от сайтов» → разрешить для `im-alive.ru`. На компьютере: настройки → «Сайты» → «Уведомления». Возможности проверяются по API браузера, название не используется для разрешения/запрета поддержки.
- **Safari на Mac:** установка на экран «Домой» не нужна; требуется поддерживающая Web Push версия Safari/macOS.

После возврата в приложение (focus, pageshow, выход из фона, восстановление сети) статус сверяется заново. Несохранённый выбор событий и тихих часов остаётся в форме. При ошибке подготовки можно повторить проверку. Запрет в браузере, неготовый service worker, сбой создания подписки и ошибка сохранения API не выдаются за успешное подключение. Сохранённую подписку можно отключить даже после запрета разрешения или отключения серверной отправки.

Перед нажатием клиент заранее проверяет владельца, ключ и готовность service worker. Если регистрация `/sw.js` отсутствует или осталась пустой после неудачной установки, подготовка восстанавливает её и ограниченно ждёт активации. `PushManager.subscribe()` вызывается непосредственно из обработчика кнопки, без отдельного `Notification.requestPermission()` и без предварительного сетевого ожидания. Подготовка не запрашивает разрешения и не меняет подписки. После создания подписки владелец, ключ и текущий endpoint проверяются повторно. Ошибка API оставляет браузерную подписку для повторной попытки, чтобы не отозвать общую подписку, уже сохранённую другой вкладкой. Она сама по себе не означает серверной регистрации.

Установка и активация service worker не зависят от подготовки офлайн-кеша. После готовности приложение отдельно запрашивает сохранение оболочки; ошибка сети, нехватка места или некешируемый ресурс не отключают push. В частности, Next/VPS отдаёт `manifest.webmanifest` с `Cache-Control: public, max-age=0, must-revalidate`: такой ответ не сохраняется для автономного повторного использования, но и не блокирует службу уведомлений. Пока ресурсы не допускают кеширование, новая офлайн-оболочка не создаётся; прежний полный кеш сохраняется. Не следует очищать данные приложения или менять VAPID-ключи для исправления ошибки «Приложение ещё готовится».

Справка платформ: [WebKit — iOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Яндекс — Android](https://yandex.ru/support/browser-mobile-android-phone/ru/personal-settings/notifications), [Яндекс — компьютер](https://yandex.com/support/browser/en/personalization/notification).

## Что отправляется

Заголовок push описывает событие: «Мохлик вернулся», «Шахтёр завершил смену», «Стройка завершена», «Ресурсы готовы» или «Пора отметиться». Текст строится по сохранённому заданию: откуда вернулся Мохлик, какая постройка завершена, какие ресурсы и в каком количестве готовы. Количества берутся из результата заказа, а не из текущего рецепта: последующее изменение каталога не меняет обещанную награду. Для нескольких категорий приходит одна сводка «Новости полянки»; длинные разделы сокращаются целиком без потери других категорий. Service worker также заменяет прежние заголовки «Я Живой» и «Мохлик» от старого API на «Новости полянки», сохраняя текст и переход.

Примеры для соответствующих сохранённых заказов:

| Событие | Заголовок | Сообщение |
|---|---|---|
| Отдельный шахтёр завершил смену | Шахтёр завершил смену | Работа в шахте завершена. Можно забрать добычу. |
| Мохлик вернулся из прежнего задания в шахте | Мохлик вернулся | Мохлик вернулся из шахты. Можно забрать добычу. |
| Возвращение с рыбалки | Мохлик вернулся | Мохлик вернулся с рыбалки. Можно разобрать улов. |
| Созревание 20 ягод | Ресурсы готовы | 20 ягод готовы к сбору. Откройте куст, чтобы Мохлик собрал урожай. |
| Завершённый сбор 20 ягод | Ресурсы готовы | Урожай собран: 20 ягод. Можно забрать в кладовую. |
| Готовые материалы | Ресурсы готовы | Готово: 2 доски и 1 верёвка. Можно забрать в кладовую. |

Системную подпись источника (например, `from Я Живой` в iOS) добавляет ОС/браузер. У Web Notifications нет настройки, чтобы убрать или переименовать её для отдельного сообщения. Для новых установок отображаемые `name`, `short_name`, `applicationName` и `appleWebApp.title` заданы как «Я Живой»; `id`, `start_url`, `scope` и существующие подписки сохранены. Старая установка iOS может сохранить прежнее имя, а пользователь может выбрать своё при установке. Автоматическое переименование старой иконки не обещается. Заголовок сайта остаётся «Я живой». После обновления сервера новый текст приходит даже старому service worker. Обновление service worker требует открытия приложения; уведомления, уже лежащие в центре уведомлений, задним числом не меняются. Перед выпуском проверьте новое одиночное уведомление и сводку на реальном устройстве, включая системное имя и открытие нужного раздела.

По умолчанию выбраны завершение стройки, возвращение Мохлика и готовое производство. Напоминание об отметке выключено: после включения оно приходит только через **больше 24 часов с последней настоящей отметки**, включая историю объединённых аккаунтов. Для профиля без отметок оно не создаётся. На одну отметку приходится максимум одно напоминание; ежедневного повторения нет.

Параметры общие для профиля: отдельные категории, тихие часы, часовой пояс IANA, максимум 1 или 2 сообщения за 24 часа, минимальный интервал от 60 до 1440 минут. Тихие часы и ограничения частоты можно выключать независимо; настройки доступны и до подключения устройства. По умолчанию тихие часы включены с 23:00 до 10:00, а ограничение частоты выключено. При включении ограничения используются сохранённые значения, изначально — максимум 2 сообщения и интервал 120 минут. Сервер применяет скользящие 24 часа, поэтому смена часового пояса и полночь не позволяют обойти включённый лимит. При `rateLimitsEnabled: false` дневной лимит и пауза не задерживают отправку; группировка событий, отдельные тихие часы и подавление во время игры сохраняются. Отсутствующее поле получает `false` в API и DEV; явно сохранённые `true` и `false` не меняются. Прежняя миграция V49 остаётся неизменной: ранее перенесённые ею настройки с включённым ограничением сохраняются.

- Готовые события объединяются в короткую сводку. Если подключено несколько браузеров, сообщение отправляется на последнее подключённое устройство, чтобы одно событие не звенело везде.
- Пока пользователь видит приложение или играет, сервер подавляет соответствующие готовые сообщения. Клиент передаёт видимость раз в минуту; учитывается также серверная игровая presence.
- Уже полученная награда, отменённая поездка, ускоренная и сразу полученная стройка не уведомляют. Завершённая стройка предлагает принять работу: сам таймер не подтверждает улучшение.
- Созревшие ягоды предлагают начать сбор. Если Мохлик занят вылазкой, прежней работой в каменоломне, рыбалкой, другим начатым сбором или старым путешествием мира, напоминание откладывается до доступности сборщика. Новая смена отдельного шахтёра (`actorId: "miner"`) не занимает Мохлика и не откладывает уведомление об урожае. Косметическая прогулка по миру не мешает. Завершившаяся обычная вылазка уже освобождает Мохлика, даже если её находки ещё не получены; другой сбор освобождает его после получения урожая. Ожидание не тратит попытку доставки или лимит сообщений.
- Созревание и собранный урожай имеют один ключ события. Уже отправленное напоминание не повторяется после сбора; если сбор начался до отправки, ожидаем завершения и сообщаем именно о собранном урожае. Волокно из сада, материалы и готовка не требуют ягодной фазы и не ждут возвращения Мохлика.
- Смешанные производственные награды перечисляются вместе. Если для готовых предметов не хватает места, текст просит освободить кладовую; вместимость учитывает также товары в рыночных объявлениях и обменах. Push никогда не утверждает, что предметы уже зачислены.
- Рыбные результаты и редкие находки не раскрываются до получения. Пуш сообщает конкретное место возвращения без скрытых предметов и количества наград.
- После тихих часов остаются только актуальные события. События старше суток подавляются; у ягод после ожидания занятого Мохлика сутки отсчитываются от доступности сбора, а не от созревания. Этот момент сохраняется в очереди и не обновляется при каждой проверке. Провайдер хранит отправленный пуш максимум 30 минут.
- Сводка только из готовых заданий отдельного шахтёра открывает шахту; будущие задания и названия маршрутов не определяют исполнителя. Смешанная сводка с путешествием открывает занятия.
- Нажатие открывает раздел, но не выполняет игровые команды. В сообщении и переходе есть публичный ID владельца; клиент проверяет его перед навигацией.

## Подключение сервера

Для production нужны HTTPS, активный service worker и постоянная пара VAPID. На iPhone/iPad нужны iOS/iPadOS 16.4+ и приложение, добавленное на главный экран; на Android поддерживаемый браузер может подключить Web Push и без установки PWA. Разрешение запрашивается только кнопкой игрока. Регистрация в Firebase, Apple Developer Program и отдельный платный сервис не требуются.

### Однократная настройка после установки 0.6.8

Уведомления и миграции V47/V49 уже входят в выпуск. API получает три переменные из `deploy/.env`:

```dotenv
WEB_PUSH_VAPID_PUBLIC_KEY=<public base64url P-256 key>
WEB_PUSH_VAPID_PRIVATE_KEY=<private base64url scalar>
WEB_PUSH_VAPID_SUBJECT=https://your-domain.example
```

[`configure-web-push.mjs`](../../scripts/configure-web-push.mjs) создаёт пару через встроенный `node:crypto`, без скачивания пакетов. По умолчанию контакт VAPID — `https://` плюс существующий `DOMAIN`; свой адрес можно задать через `--subject mailto:admin@example.com`. Скрипт меняет только три VAPID-строки, сохраняет остальные настройки и комментарии, пишет файл атомарно с правами `0600` и не выводит ключи. Повторный запуск проверяет существующую пару и сохраняет её. Частично заполненная, повторяющаяся или некорректная конфигурация останавливает настройку без замены ключей. Одновременные запуски защищены файлом `.env.web-push.lock`; после аварийного завершения сначала убедитесь, что другой процесс настройки не работает, затем удалите оставшийся lock.

Если Node уже установлен на сервере, из каталога проекта достаточно выполнить:

```bash
node scripts/configure-web-push.mjs
```

Вариант без установки Node на хост: команда ниже использует Node 24 из **уже запущенного образа web**. У временного контейнера выключена сеть; ему доступны сам скрипт только на чтение и каталог `deploy` для записи `.env`. Выполняйте блок под владельцем `~/zhiv-app` и `deploy/.env`: `sudo` используется только для Docker, а `--user` сохраняет UID/GID владельца файлов. При запуске от root скрипт сохраняет прежнего владельца `.env`.

```bash
(
  set -euo pipefail
  cd ~/zhiv-app
  docker_command=(docker)
  if (( EUID != 0 )); then docker_command=(sudo docker); fi
  dc() { "${docker_command[@]}" compose --env-file deploy/.env -f deploy/compose.yml "$@"; }

  web_container="$(dc ps -q web)"
  test -n "$web_container"
  web_image="$("${docker_command[@]}" inspect --format '{{.Image}}' "$web_container")"
  "${docker_command[@]}" run --rm --pull never --network none --read-only \
    --user "$(id -u):$(id -g)" \
    --mount "type=bind,src=$PWD/deploy,dst=/push-config" \
    --mount "type=bind,src=$PWD/scripts/configure-web-push.mjs,dst=/configure-web-push.mjs,readonly" \
    --entrypoint node "$web_image" /configure-web-push.mjs --env /push-config/.env

  dc config --quiet
  dc up -d --no-deps --no-build --force-recreate --wait --wait-timeout 120 api
  dc exec -T api sh -c 'test -n "$WEB_PUSH_VAPID_PUBLIC_KEY" && test -n "$WEB_PUSH_VAPID_PRIVATE_KEY" && test -n "$WEB_PUSH_VAPID_SUBJECT"'
  dc exec -T api curl -fsS --max-time 20 http://127.0.0.1:8080/readyz
)
```

После короткой команды с локальным Node примените те же последние четыре `dc`-команды, предварительно определив `docker_command` и `dc` как в блоке выше. При уже установленной 0.6.8 пересборка, повторные миграции и перезапуск web не нужны. `docker compose restart api` **не обновляет переменные окружения**: требуется пересоздание API через `up --force-recreate`. API при запуске проверяет совместимость пары ключей. `/readyz` подтверждает готовность API/БД; он не проверяет доставку push провайдером. Фактический статус подключения сервера возвращает authenticated `GET /api/v1/notifications` в `delivery.configured`, а готовность устройства — `subscription.subscribed` вместе с локальной подпиской браузера. Закрытый ключ в API-ответ не попадает.

### Подключение телефона и первая доставка

1. **iPhone/iPad:** откройте сайт в Safari → «Поделиться» → «На экран Домой», затем запустите приложение с появившейся иконки. **Android:** откройте сайт в поддерживаемом браузере, например Chrome, или установленное приложение.
2. Войдите в нужный профиль → шестерёнка → «Уведомления» → **«Подключить на устройстве»** и разрешите системный запрос. Статус должен стать «Подключены на этом устройстве». При прежнем отказе сначала разрешите уведомления в настройках браузера/устройства.
3. Выберите нужную категорию, сохраните настройки. Для первой проверки временно выключите тихие часы и ограничения частоты. Запустите короткое производство, поездку или стройку и закройте приложение до завершения. Не забирайте результат из другого браузера: полученное или уже показанное в игре событие подавляется. Планировщик проверяет очередь каждые 30 секунд, а доставка дополнительно зависит от браузера, сети и ОС.
4. Нажмите на полученный пуш: приложение должно открыть соответствующий раздел. Затем верните нужные тихие часы. Перед выпуском отдельно проверьте iOS PWA, Android Chromium и Firefox, отключение категории и выход из аккаунта.

Во время видимой игры push намеренно подавляется; последняя активность учитывается ещё 2 минуты после закрытия. Для надёжной первой проверки выбирайте событие, которое закончится хотя бы через 5 минут после закрытия приложения. Если подключено несколько устройств, сообщение получит последнее подключённое. По умолчанию включены стройка, возвращение Мохлика и производство; тихие часы действуют с 23:00 до 10:00 в выбранном часовом поясе.

Если все три переменные отсутствуют, настройки доступны, но API честно возвращает `configured: false`, `reason: "not_configured"`; подключение возвращает 503 `PUSH_NOT_CONFIGURED`. Частичная конфигурация или несовпадающая пара ключей останавливает запуск с понятной ошибкой. Пара ключей должна оставаться постоянной между перезапусками. При её замене пользователям потребуется переподключить устройства.

**Не включайте `ECE_KEYLOG=1`.** Отладочный режим стороннего шифровальщика печатает ключевой материал; API запрещает запуск отправителя в таком окружении.

## Устройство и безопасность

Основные файлы:

- [`notification-browser.ts`](../../features/notifications/notification-browser.ts): подготовка и подписка из пользовательского жеста, ограничения ожидания и защита владельца.
- [`use-notification-device.ts`](../../features/notifications/use-notification-device.ts): сверка при возврате, этапы подключения и защита состояния формы.
- [`notification-device-card.tsx`](../../features/notifications/notification-device-card.tsx): разрешение, подтверждённое подключение и ошибки рядом с кнопкой.
- [`Notifications.kt`](../../apps/api/src/main/kotlin/ru/zhiv/notifications/Notifications.kt): DTO, категории, ограничения, тихие часы, проверка endpoint.

Расписание обновляется в той же транзакции, что и экономический профиль. Рабочий цикл выбирает уже материализованные сроки через частичный индекс, а не сканирует JSONB всех игроков. На одного игрока одновременно может отправляться только согласованная сводка: блокировка аккаунта, постоянная запись отправки до сети и повторная проверка источника после резервирования. Перед отправкой заново читаются задание, его фаза, занятость Мохлика и вместимость кладовой. Удаление задания в промежутке убирает сообщение; начавшаяся поездка откладывает сбор, а не блокирует готовые независимые заказы.

Подписка принадлежит точной auth-сессии и аккаунту. Выход, восстановление с отзывом сессий, перенос сессии, удаление или блокировка профиля отключают её через БД. Отдельный проверочный запрос нельзя использовать, чтобы удалить подписку другого аккаунта. При объединении профилей настройки/подписки источника не переносятся. Если сохранённая сессия целевого профиля остаётся действительной, её подписка сохраняется.

Разрешены только HTTPS endpoint известных служб Google, Mozilla, Apple и Microsoft. HTTP redirects выключены, connect timeout 2 секунды, request timeout 3 секунды. URL, ключи, payload и ответы провайдера не журналируются. Используются `web-push:5.1.2` без устаревших HTTP-транзитивных зависимостей, Bouncy Castle 1.83 и jose4j 0.9.6. AES128GCM задаётся явно; устаревшая подмена FCM endpoint и заголовок Crypto-Key из библиотеки не используются.

404/410 удаляют неработающую подписку. Явные 429/5xx повторяются максимум три раза с задержками. После сетевого timeout нельзя узнать, принял ли провайдер сообщение: такая попытка помечается `uncertain` и не повторяется, чтобы избежать дубля. После аварийного перезапуска так же обрабатываются зависшие резервации. Это сознательный выбор в пользу отсутствия спама: гарантировать «ровно один раз» по Web Push нельзя. Дневной лимит учитывает успешные и неопределённые отправки. История попыток хранится 32 дня; строки живых заданий нужны до их получения для дедупликации.

## API

- `GET /api/v1/notifications?expectedOwnerPublicId=...`
- `PUT /api/v1/notifications/preferences` с `{ expectedOwnerPublicId, preferences }`
- `POST /api/v1/notifications/subscriptions` с `{ expectedOwnerPublicId, subscription: { endpoint, keys: { p256dh, auth } } }`
- `DELETE /api/v1/notifications/subscriptions` с `{ expectedOwnerPublicId, endpoint }`
- `POST /api/v1/notifications/presence` с `{ expectedOwnerPublicId }`

Snapshot: `{ ownerPublicId, preferences, delivery: { configured, publicKey, reason }, subscription: { subscribed } }`. `subscribed` относится к текущей auth-сессии. Клиент дополнительно проверяет реальный `PushSubscription` этого браузера. Все ответы `no-store`; закрытый VAPID-ключ никогда не возвращается.

Локальный DEV сохраняет параметры, но возвращает `not_configured`, пока реальный серверный контур не подключён. Он не имитирует доставку или разрешение браузера.

## Проверки

`NotificationRulesTest` проверяет ограничения, зоны/DST и SSRF allowlist; `NotificationMessagesTest` проходит рецепты, занятия и постройки каталога, сохранённые количества, русские формы, смешанные результаты и скрытые находки. `NotificationReadinessTest` проверяет доступность сборщика. `WebPushSenderTest` проверяет подпись VAPID и полное шифрование/расшифровку payload на одноразовых ключах без отправки в интернет. `JdbcNotificationRepositoryIntegrationTest` проверяет подписки, owner fence, отмену/получение, созревание и сбор ягод, повторную проверку перед отправкой, группировку, тихие часы, лимиты, наличие пользователя, строгие 24 часа, объединённую историю, два worker, retry, неоднозначную отправку и удаление аккаунта. Для него нужен PostgreSQL 18 (Testcontainers или явно заданный тестовый `TEST_DATABASE_URL`). Тесты не заменяют доставку на реальное устройство.
