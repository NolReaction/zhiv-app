# Сбои и восстановление

Релиз **0.6.1**. Эта памятка описывает существующие механизмы и следующие отдельные задачи. Наличие правила Prometheus не означает, что настроена доставка уведомлений человеку.

## Что уже доступно

- `/admin` → «Сбои пользователей»: 1/6/24 часа, 7/30 дней; поиск по имени/публичному коду, источник браузер/API, код события. Общее число записей, сумма повторов и число аккаунтов считаются по всей отфильтрованной истории, а не по открытой странице.
- Время события и время приёма раздельны; браузер доставляет очередь позднее. `SYNC_RECOVERED` означает возобновление отправки, **не подтверждение сохранения всей очереди**.
- Копирование request ID и подсказка «Что проверить» у каждого события. События `WORLD_MAP_FAILED/TIMEOUT` и `WORLD_CHARACTER_FAILED/TIMEOUT` отличают загрузку графики от недоступности API.
- Загрузка изображений имеет срок 15 секунд, ошибочная попытка удаляется из кеша. Повтор не меняет серверные ресурсы. Закрытие карты отменяет ожидание и не оставляет контроллер персонажа или цикл отрисовки.
- В Prometheus добавлены устойчивые сигналы: 429 >5% и минимум 10 за 5 минут в течение 2 минут; p95 API >2 секунд при минимум 30 запросах за 5 минут в течение 3 минут. Существующие 5xx, недоступность API, место, память и отклонённые игровые тапы сохранены.
- Метрики сервера и история событий имеют разные сроки: 30 дней событий не расширяют автоматически доступный период Prometheus.

## Первые действия при сообщении игрока

1. Записать публичный код игрока, примерное время с часовым поясом, экран/действие и устройство. Пароли, резервные коды и cookie не нужны.
2. Выбрать подходящий период, найти код игрока, посмотреть события до и после сбоя. Сравнить `occurredAt` и `receivedAt`, размер неподтверждённой очереди, HTTP-код и request ID.
3. Проверить масштаб: снять фильтр игрока, оставить код сбоя и период. Число аккаунтов помогает отличить локальную проблему от массовой. Сумма сообщений не равна числу независимых инцидентов.
4. Сопоставить с 5xx/429/задержкой API и журналом по request ID. При проблеме графики проверить доступность конкретных файлов, а не только `/readyz`.
5. При проблеме сохранения не просить очистить данные браузера или создать новую игровую сессию до разбора старой очереди. Проверить серверные подтверждения и идемпотентные повторы. Не компенсировать очки на глаз.
6. После исправления проверить успешное подтверждение очереди, сохранённый рекорд на другом устройстве и прекращение новых ошибок. Зафиксировать причину и действие, которое предотвратит повторение.

## Следующие задачи по отказоустойчивости

| Приоритет | Изменение | Критерий готовности |
|---|---|---|
| P1 | Внешняя проверка главной страницы и `/readyz` с отдельного узла | Полное падение VPS обнаруживается независимо от Prometheus на нём |
| P1 | Alertmanager и согласованный канал дежурного | Тестовый инцидент доставляется, повторения группируются, уведомление о восстановлении приходит |
| P1 | Автоматическая резервная копия вне VPS и учебное восстановление | Зафиксированы дата последнего успешного бэкапа, длительность полного восстановления и проверка данных |
| P2 | Идентификаторы сборок web/API в диагностике | Видно несовпадение версий после обновления; SHA не подменяется неизменным `0.6.0` |
| P2 | Возраст старейшей неподтверждённой пачки и время последнего подтверждения | Можно отличить растущую очередь от краткой задержки и предупредить истечение срока доставки |
| P2 | Счётчики пропущенных диагностических событий по ограниченной причине | Видно, когда сама диагностика перегружена; аккаунты и request ID не становятся метками метрик |
| P2 | Карточка инцидента: новый → разбирается → исправлен | Назначены ответственный, временной интервал, причина и ссылка на исправление |
| P3 | Постепенное обновление и проверенный откат совместимых версий | Проверяются API, графика и сохранение очереди; откат приложения не откатывает данные пользователей |

В диагностике сохраняются коды и ограниченные структурированные поля. Не добавлять сырые cookie, токены, резервные коды, полный URL, произвольные сообщения или stack trace из браузера. Общие логи должны иметь лимит и срок хранения; запись диагностического события не должна блокировать игровой запрос.

Правила и инструменты для следующего этапа: [Prometheus alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/), [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/), [Blackbox Exporter](https://github.com/prometheus/blackbox_exporter), [instrumentation practices](https://prometheus.io/docs/practices/instrumentation/). Внешние проверки и доставка уведомлений этим изменением ещё не включены.
