# Сброс игры с сохранением аккаунтов

Подготовлено для обновления экономики 0.6.9. Само добавление скрипта, обновление
приложения и миграции **не запускают сброс**. Рабочая база не очищалась.
Это отдельная операция владельца после проверки и развёртывания нужного выпуска.
`reset-user-data.sh` и `reset-database.sh` для этой задачи не подходят: они удаляют
аккаунты и связи друзей.

## Граница очистки

Полный проверяемый список находится в `scripts/reset-game-progress.sql`.
Скрипт рассчитан на схему 50: новая база из B49 с последующей V50 или существующая
с историей V1–V50. V50 меняет только инициализатор начального хозяйства; состав
сохраняемых и очищаемых таблиц остаётся прежним.
Исходная история Flyway сохраняется целиком; этот сброс не сворачивает её в baseline.
Любая другая версия, неуспешная миграция или
неизвестная таблица останавливает даже предварительный просмотр. После слияния
новых миграций список и проверки необходимо пересмотреть; история Flyway сохраняется.

| Данные | Результат |
|---|---|
| Аккаунты, публичные ID, имена, аватары, язык и часовой пояс | Сохраняются полностью |
| ВК/почта, активные входы, резервные коды, подтверждения и история объединения аккаунтов | Сохраняются полностью |
| Друзья, группы, приглашения, избранное, личные имена и настройки доступа | Сохраняются полностью |
| Отметки «Я живой» и история их получателей | Сохраняются как история сервиса заботы |
| Модерация, баны, наблюдение, журнал администратора, обращения, инциденты | Сохраняются полностью |
| Подписки и настройки push, напоминания об отметках, журнал отправок | Сохраняются полностью |
| История получения промокодов | Сохраняется: уже использованный подарок нельзя получить повторно |
| Учёт времени онлайн, анти-AFK наблюдение и служебная метка сбора кликов | Сохраняются; активные игровые подключения закрываются |
| Хозяйство, валюта, склад, рыба, удочки/крючки/наживки, еда, заказы, постройки и выполняемые задания | Очищаются |
| Коллекции, одежда/игровые предметы, достижения, награды, клики, серии и рейтинг | Очищаются |
| Старый мир, его ресурсы и поездки, память/положение Мохлика и жителей | Очищаются |
| Объявления рынка, обмены, витрины, оборот, квитанции игровых команд, экономические журналы и старые конвертации | Очищаются |
| Ожидающие и исторические уведомления о стройке, производстве и путешествиях | Очищаются, чтобы не приходили сообщения о старых заданиях |

Полностью опустошаются 22 явно перечисленные игровые таблицы; в шести таблицах
игровые данные заменяются начальными, но сохраняется защита монотонных версий.
Ещё 41 таблица сохраняется целиком, в `notification_events` удаляются игровые события,
а напоминания об отметках восстанавливаются в точности после срабатывания штатных
триггеров инициализации. Нет `CASCADE`,
удаления схемы, изменения `app_users` или отзыва `app_sessions`. До и после
очистки сравниваются отпечатки всех строк сохраняемых таблиц, истории миграций и
напоминаний об отметках. Несовпадение откатывает всю транзакцию.

Игрокам с прежними профилями/квитанциями сразу создаётся начальное хозяйство;
для аккаунтов без игрового состояния остаётся обычная серверная инициализация.
Применяется тот же SQL-инициализатор, что при первом входе в игру, с актуальными
правилами чтения каталога: 100 монет, 0 жемчуга, 3 бревна, 5 камней, дом/куст/кладовая
первого уровня и первый из четырёх учебных заказов. Старые ресурсы не конвертируются: вместо старого мира
создаётся начальное состояние. Новые квитанция стартового набора и нулевая
граница конвертации не позволяют повторно выдать набор при последующем удалении
только профиля хозяйства. Ранее использованные
промокоды остаются использованными. Ежедневные и игровые награды начинают новый цикл.
Награды за сохранённые отметки/друзей/настройки безопасности могут снова открыться
по существующим правилам — сама история этих действий не обнуляется.

## Предварительный просмотр

Из проверенного checkout на VPS с работающим PostgreSQL:

```bash
cd ~/zhiv-app
sudo bash scripts/reset-game-progress.sh
```

То же самое: `sudo bash scripts/reset-game-progress.sh --preview`.
Режим по умолчанию использует транзакцию `READ ONLY`, проверяет схему и печатает
только названия таблиц и количество строк: `CLEAR` или `KEEP`. Он не останавливает
сайт, не создаёт backup и не меняет данные. Содержимое аккаунтов и секреты не выводятся.

## Будущее выполнение

Не запускать одновременно с деплоем, миграциями или другой очисткой. На диске
должно хватать места для полного dump и его временного восстановления.
После обслуживания перезагрузить игровые вкладки, чтобы обновилась и локальная
декоративная сцена. Безопасность игровых команд не зависит от удаления браузерных
данных: старые версии отклоняются сервером.

```bash
cd ~/zhiv-app
sudo bash scripts/reset-game-progress.sh --confirm-reset-game-progress
```

Этот явный флаг включает очистку. Скрипт проверяет схему, останавливает Caddy/web/API,
делает закрытый dump в `../zhiv-backups`, полностью восстанавливает его в отдельную
временную базу и **репетирует на копии ту же очистку с проверкой сохранности данных**.
Только после успеха повторяет транзакцию на рабочей `zhiv`, запускает те же контейнеры
без сборки/миграций и проверяет `/readyz`. Оригинальная копия остаётся на диске с
правами только для владельца. Она содержит старые аккаунты и игровые данные;
операция не стирает резервные копии.

При ошибке не повторять команду вслепую: она сообщает путь к dump и факт успешного
COMMIT, если он уже произошёл. Сервисы могут остаться остановленными. После выяснения
причины для запуска без повторной очистки:

```bash
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d --no-deps --no-build --no-recreate --wait --wait-timeout 120 api web caddy
```

Запуск контейнеров не восстанавливает прогресс. Для восстановления исходного dump
используется отдельная процедура из [полного сброса базы](reset-database.md#если-произошла-ошибка).
Она заменяет текущую базу целиком. Не использовать `down -v`.

## Ограничения и проверка

- Обслуживается серверный PostgreSQL-контур VPS. Данные отдельной локальной/Sites
  среды, файлы аватаров и браузерные настройки скрипт не удаляет.
- Незавершённые команды могут пережить перезагрузку в `sessionStorage`. Поэтому
  ревизии хозяйства, старого мира, памяти леса и версия согласия на рейтинг
  **не обнуляются**. Скрипт выбирает максимум прежних профилей и сохранённых
  квитанций пользователя и устанавливает следующую версию. Проверяется запас до
  предела безопасного целого; при исчерпании операция откатывается. Старая команда
  хозяйства/мира/памяти получает конфликт версии, клиент снимает неподтверждённый
  запрос и читает новое состояние. Старый запрос включения рейтинга также
  отклоняется; после сброса рейтинг пуст и участие выключено.
- Игровые сессии кликов удаляются, поэтому пакеты старой игровой сессии больше
  не принимаются. Это не сессии входа: cookies авторизации сохраняются.
- Запрос ежедневной/достиженческой награды не содержит ревизию хозяйства.
  Его поздний повтор может получить обычную доступную награду нового цикла;
  действуют штатные ограничения одной выдачи, дополнительный дубль не создаётся.
- Экономические ресурсы серверные, однако живая вкладка может вновь сохранить
  своё декоративное состояние леса; локальные подсказки/настройки камеры не входят
  в БД. Закрытие старых вкладок устраняет и этот источник старого состояния.
- `notification_batches` содержит только историю резервирования и доставки,
  без готового текста push. Диспетчер выбирает события из `notification_events`
  и не повторяет отправку старых `sending`-пакетов после рестарта. Сохранённая
  история не отправит старое игровое событие. Уже принятое внешним push-сервисом
  сообщение до остановки API может ещё доставиться в пределах его TTL (30 минут).
- После запуска проверить существующий вход, друзей и группы, начальный склад,
  отсутствие старых заданий/объявлений и новые награды. В отдельной копии до реального
  обслуживания также проверить обновление с текущей версии приложения.
- `node --test tests/reset-game-progress.test.mjs` проверяет границу таблиц и
  порядок защит в оболочке без подключения к БД. `JdbcGameProgressResetIntegrationTest`
  выполняет SQL на настоящем PostgreSQL 18 через Testcontainers, включая сохранность
  аккаунтов/входов/дружбы, отказ при неизвестной схеме, откат при нарушении
  сохранности, предел ревизий и отказ реальных репозиториев от старых игровых
  запросов. Для него нужен Docker.

Это подготовка операции, а не обязательное условие установки рыбной переработки.
