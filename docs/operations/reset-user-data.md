# Полная очистка пользователей после тестового запуска

Это разовая операция по явному решению владельца. Она удаляет **всех пользователей,
отметки, серии, связи, группы, приглашения, подписи, сеансы, привязки ВК/почты,
резервные коды, обращения игроков с журналом обработки, память Мохлика, настройки и подписки уведомлений,
очередь отправки, историю получения промокодов и незавершённые попытки входа**. Все начинают с нового профиля. Это не сброс только игрового прогресса: аккаунты и способы входа тоже удаляются.
DNS, настройки SMTP/ВК, секреты, схема БД, роли, миграции и Docker volumes сохраняются.
Обычный вход в другом браузере такой очистки не требует. Для удаления всей схемы
и повторного выполнения миграций использовать [полный сброс базы](reset-database.md).

Сначала обновить код и пересобрать API/web. Затем выполнить на VPS из `~/zhiv-app`:

```bash
sudo bash scripts/reset-user-data.sh --confirm-delete-all-users
```

Скрипт проверяет наличие включённого входа ВК или почты и отключённого старого
создания профиля по имени (`POST /api/v1/bootstrap` возвращает 410). Потом останавливает
Caddy/web/API, оставляет PostgreSQL работающим, делает закрытую резервную копию
в `../zhiv-backups` и полностью восстанавливает её в отдельную временную БД.
Только после успешного восстановления запускается транзакционная очистка.
В схеме V72 ожидаются 82 таблицы пользовательских данных, включая состояние обучения и личные данные соседа,
и шесть служебных таблиц: `game_tap_collection_metadata`, `managed_promo_codes`,
`gameplay_generations`, `gameplay_reset_runs`, `neighbor_settings`, `neighbor_global_usage`. Неизвестная таблица или версия схемы останавливает операцию.
Поддерживаются новая база B49 → V50–V72 и существующая база с историей V1–V72.
Скрипт сохраняет исходный журнал Flyway целиком и не заменяет старую историю baseline-записью.
Очистка проверяет пустоту всех 82 пользовательских таблиц, точную сохранность истории Flyway,
метки начала сбора кликов, настроек промокодов, поколения игры, журнала однократных сбросов,
настроек соседа и глобального бюджета его выкупов.
Акции, включая удалённые записи, сохраняются; история активаций удаляется вместе со всеми аккаунтами.
Не запускать скрипт при параллельном деплое или миграции.

При ошибке копия сохраняется, а скрипт не пытается автоматически исправить сбой.
Если ошибка произошла при запуске сервисов, часть контейнеров уже может работать.
Путь к копии выводится в терминал. Устранить причину и для возврата сайта выполнить:

```bash
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d --no-deps --no-build --no-recreate --wait --wait-timeout 120 api web caddy
```

Если ошибка произошла после успешного COMMIT, данные уже очищены; запуск контейнеров
не восстанавливает их из копии. Полное восстановление — отдельная операция.
Не использовать `down -v`, не удалять рабочий volume и не отключать DELETE-триггеры.
Копия на том же VPS защищает от ошибки этой операции; для защиты от потери сервера
нужна также копия вне VPS, см. `operations.md`.

После очистки открыть сайт и войти одним способом, затем привязать второй в
«Профиль → Способы входа». Уже отдельно созданные профили автоматически не сливаются; для них используется
отдельное подтверждённое объединение аккаунтов.
Новые пользователи могут войти через ВК/почту; резервный код по-прежнему остаётся
дополнительным способом восстановления для тех, кто его создал.
