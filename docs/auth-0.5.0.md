# Вход в 0.5.0

Один профиль поддерживает несколько браузеров. Telegram и подтверждённый email связываются с прежним `app_users.id`; вход выдаёт новую HttpOnly-сессию, не отзывает остальные и не меняет связи, группы и отметки. Игровые рекорды, которые уже хранились локально в браузере, по-прежнему локальные.

## Первый переход существующего пользователя

1. Открыть действующий профиль → «Профиль» → «Способы входа».
2. Привязать Telegram и/или почту, подтвердив владение.
3. На другом устройстве выбрать тот же способ входа. Оба устройства остаются подключены.

Неизвестная внешняя идентичность при обычном входе не создаёт пользователя автоматически. Новый профиль создаётся только после явного выбора «Создать профиль» и ввода имени. Совпадение имени или Telegram username не объединяет аккаунты. Занятую идентичность нельзя переприсвоить другому профилю.

Резервный код остаётся аварийным восстановлением: он одноразовый и закрывает прежние сессии. Он не нужен для обычного входа с привязанным Telegram/email. Если прежний профиль закрыт везде и нет ни привязки, ни кода, автоматически установить его владельца невозможно.

## Настройка Selectel

Код не содержит реальных ключей и не включает провайдеров до настройки. Пока провайдеры отключены, старые профили, сессии и восстановление продолжают работать. Для Telegram и SMTP контейнер API подключён к отдельной исходящей сети; порты API и PostgreSQL наружу не опубликованы.

Перед установкой релиза сделать резервную копию PostgreSQL обычным процессом проекта. Обновление применяет миграции V14 и V15. Не удалять volume PostgreSQL и не использовать `down -v` на рабочем сервере.

Создать на сервере отдельный каталог только для ключей авторизации:

```bash
cd ~/zhiv-app
mkdir -p deploy/.secrets/auth
chmod 700 deploy/.secrets
chmod 755 deploy/.secrets/auth
```

Он подключается к API как `/run/auth-secrets`. Файлы паролей БД из родительского каталога через этот mount недоступны. Значения секретов никогда не отправлять в чат или GitHub. Для новых файлов использовать режим `444`; родительский `deploy/.secrets` с правами `700` закрывает доступ другим пользователям хоста. Подкаталог `auth` имеет `755`, чтобы отдельный UID контейнера мог проходить по нему после bind mount.

### Telegram

В BotFather создать или выбрать бота → Bot Settings → Web Login (название раздела может отличаться). Настроить официальное OIDC-приложение Telegram Login:

- Origin: `https://im-alive.ru`
- Redirect URI: `https://im-alive.ru/api/v1/auth/telegram/callback`
- Получить **Client ID и Client Secret**. Это параметры Telegram Login, а не подстановка bot token вместо Client Secret.
- Сохранить Client Secret в `deploy/.secrets/auth/telegram_client_secret`.

В `deploy/.env`:

```dotenv
TELEGRAM_CLIENT_ID=your-client-id
TELEGRAM_CLIENT_SECRET_FILE=/run/auth-secrets/telegram_client_secret
```

Номер телефона и разрешение писать пользователю не запрашиваются. Используется `scope=openid`, подписанный `sub`, Authorization Code + PKCE, одноразовые state/nonce и привязка к браузеру. Callback фиксирован конфигурацией, не собирается из входящего Host.

### Почта

Нужен SMTP-сервис с разрешённой отправкой от выбранного адреса. Настроить подтверждение домена отправителя, SPF/DKIM по инструкции сервиса. Эти записи не заменяют A-запись приложения.

Создать `smtp_password` с паролем SMTP в том же каталоге. Сгенерировать отдельный секрет защиты цифровых кодов:

```bash
node scripts/create-auth-secret.mjs
```

В `deploy/.env`:

```dotenv
SMTP_HOST=smtp.your-provider.example
SMTP_PORT=587
SMTP_TLS_MODE=starttls
SMTP_USER=your-smtp-user
SMTP_PASSWORD_FILE=/run/auth-secrets/smtp_password
SMTP_FROM=login@im-alive.ru
AUTH_CODE_SECRET_FILE=/run/auth-secrets/code_secret
```

Для TLS с начала соединения использовать `SMTP_PORT=465` и `SMTP_TLS_MODE=implicit`. Незащищённый SMTP не поддерживается. Код действует 10 минут, максимум пять проверок; новый код можно запросить не чаще раза в минуту и пяти писем на адрес в час. Дополнительно действует ограничение попыток по IP. Коды хранятся через HMAC, секрет HMAC не находится в БД. Каждый код связан с запросом и браузером, где он был запрошен. Перезагрузка страницы во время ввода может потребовать запроса нового кода.

После настройки и проверки прав файлов обновить контейнеры из проверенного коммита:

```bash
sudo docker compose --env-file deploy/.env -f deploy/compose.yml config --quiet
sudo docker compose --env-file deploy/.env -f deploy/compose.yml up -d --build api web caddy
curl --fail https://im-alive.ru/api/v1/auth/options
```

Ответ показывает реально включённые способы: `{"telegram":true,"email":true}`. Можно включать их по одному. Не использовать команду `compose config` без `--quiet` для пересылки настроек.

## Проверка с настоящими провайдерами перед объявлением друзьям

- Привязать Telegram к существующему тестовому профилю. Войти тем же Telegram из второго браузера и проверить совпадение публичного ID и сохранение обеих сессий.
- Повторить с email, проверить доставку в реальные почтовые ящики, ошибочный и просроченный код.
- Проверить Telegram iOS/Android, обычные Safari/Chrome, отмену подтверждения и возврат на сайт. Установка PWA зависит от браузера и не является условием входа.
- В «Устройствах» завершить второй сеанс, затем проверить «Выйти на остальных устройствах»: текущий остаётся подключён.
- Проверить, что отказ от входа и повторный callback не создают профиль, а конфликт привязки не меняет владельца.

Локальные и CI-тесты проверяют протокол, маршруты и БД с изолированными данными; они не заменяют реальную доставку SMTP и подтверждение в Telegram. Следующее расширение — смена/отвязка способа входа с повторным подтверждением; в 0.5.0 привязанный идентификатор не заменяется автоматически.
