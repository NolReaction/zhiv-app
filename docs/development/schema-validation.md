# Валидация контрактов

Общие TypeScript-контракты используют исправленный runtime Zod 4.6.7 из `zod`. Импорты `zod/v3` не устраняют уязвимость прежнего runtime и здесь не используются. Ktor сохраняет собственную проверку входных данных.

При изменении схем сохраняйте договорённости старых снимков и журналов:

- `.prefault(...)` проверяет и копирует значение по умолчанию, как прежний Zod 3. Это особенно важно для вложенных карт репутации, маршрутов и рецептов: `.default({...})` в Zod 4 может возвращать общие вложенные ссылки между новыми состояниями.
- `z.partialRecord(enum, value)` допускает неполную карту известных жителей. `z.record(enum, value)` требует все ключи и не подходит старым сохранениям с одним жителем или пустой картой.
- `z.guid()` сохраняет прежнюю проверку идентификатора вида `8-4-4-4-12`. Там, где контракт команды требует именно UUID v4, дополнительная проверка версии и variant-битов сохраняется. Это разные договорённости; не ужесточайте чтение старых журналов случайно при обновлении библиотеки.
- Двухаргументный `z.record(key, value)` явно задаёт допустимые ключи. Строгие командные объекты по-прежнему отвергают неизвестные поля.

Регрессии: `tests/schema-runtime-compatibility.test.mjs` проверяет независимость новых состояний, неполные карты жителей, старые GUID и строгие UUID v4, а также ранний отказ ограниченного массива до обхода чрезмерного входа. Дополнительно нужны обычные API, журналы повторов, награды и полный веб-набор.

Основание: [официальное руководство миграции](https://zod.dev/v4/changelog), [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). Ограничения размера HTTP-запросов и игровой валидации остаются самостоятельными проверками.
