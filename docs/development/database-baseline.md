# Начальная схема PostgreSQL и история обновлений

Источник — `apps/api/src/main/resources/db/migration/`. Обычный Flyway использует `classpath:db/migration` и рекурсивно видит вложенную историю.

| Файлы | Назначение |
|---|---|
| [B49__current_schema.sql](../../apps/api/src/main/resources/db/migration/B49__current_schema.sql) | Создание пустой БД сразу в итоговой схеме версии 49: таблицы, ограничения, индексы, функции и триггеры |
| [history/V1–V49](../../apps/api/src/main/resources/db/migration/history/) | Неизменённая цепочка для обновления старых БД и исторических тестов |
| [V50__first_stage_economy.sql](../../apps/api/src/main/resources/db/migration/V50__first_stage_economy.sql) | Новый старт: 100 монет, 3 бревна, 5 камней и четыре последовательных учебных заказа; существующие профили и задания не изменяются |
| [V51__independent_mining_jobs.sql](../../apps/api/src/main/resources/db/migration/V51__independent_mining_jobs.sql) | Увеличивает только предел jobs с 16 до 18 для независимых работ Мохлика, шахты и строителя; состояния не переписываются |
| Будущие `V52__…sql` и выше в корне | Следующие изменения, применимые после обоих поддерживаемых путей |

На пустой БД Flyway исполняет B49 и записывает выполненную миграцию типа `SQL_BASELINE`, версии 49,
затем применяет V50 и V51. Текущий начальный запуск даёт три успешные записи, итоговая версия — 51. Исторические переносы данных, конвертации валют и backfill V1–V49 для нового старта не воспроизводятся. Приложение создаёт пользовательские профили штатными правилами.

БД с существующей историей Flyway продолжает V-цепочку до V51; B49 к ней не применяется. Перенос SQL в `history/` сохраняет имена, версии, содержимое и checksums. Уже записанные строки `flyway_schema_history` не переписываются. Для заполненной БД без истории нельзя подменять проверку схемы включением `baselineOnMigrate` или запуском команды `baseline`: это отдельная задача принятия под управление, которую текущий механизм не выполняет.

## Следующее изменение

1. Добавьте следующий свободный `V<N>__description.sql` в корень `db/migration/`; после текущего этапа это V52. Он должен работать на результате обоих путей: V1–V51 и B49 → V50 → V51.
2. Историю V1–V49 и опубликованные V50/V51 не редактируйте. После публикации B49 также неизменяем: исправление оформляется следующей V-миграцией, чтобы свежая и существующая БД получали одинаковое изменение.
3. Проверьте пустую БД, обновление заполненной исторической БД, повторный запуск Flyway и проверку API под ограниченной runtime-ролью. Сравнивайте не только таблицы, но и ограничения, индексы, функции, триггеры и необходимые права.
4. Исторические тесты с `target` ниже 49 должны читать только `classpath:db/migration/history`. Обычный путь читает весь `classpath:db/migration`; не отключайте baseline в production ради тестовой фикстуры.

Это SQL baseline-миграция, а не ручная пометка существующей схемы командой Flyway `baseline`. Новые baseline более поздних версий требуют отдельного проверенного этапа; текущий файл не превращается в постоянно редактируемый дамп.

## Независимая шахта и ограничение jobs

Каталог v7 добавляет `actorId`, курс `stageOrders` и приватный `minerRareDropState` через JSON-значения по умолчанию. Для этих полей backfill существующих профилей не требуется. V51 нужна для реального ограничения PostgreSQL: пять обычных производств с тремя местами могут хранить 15 jobs, параллельно идут один job Мохлика, один шахты и одна стройка — всего 18. Миграция меняет только верхнюю границу массива в `economy_profiles_state_check6`; остальные проверки сохраняются. Слияние аккаунтов с незавершёнными jobs остаётся запрещённым, поэтому не создаёт сумму очередей сверх предела.

## Данные и эксплуатация

Наличие B49 не вызывает сброс и не является командой очистки. Обычный запуск, миграция и деплой сохраняют аккаунты, авторизацию, друзей, служебные данные и существующий игровой прогресс. Разрешённая очистка только игрового прогресса выполняется отдельной эксплуатационной процедурой с backup и проверкой сохранения данных; SQL истории и baseline для этого не редактируются.
