# Начальная схема PostgreSQL и история обновлений

Источник — `apps/api/src/main/resources/db/migration/`. Обычный Flyway использует `classpath:db/migration` и рекурсивно видит вложенную историю.

| Файлы | Назначение |
|---|---|
| [B49__current_schema.sql](../../apps/api/src/main/resources/db/migration/B49__current_schema.sql) | Создание пустой БД сразу в итоговой схеме версии 49: таблицы, ограничения, индексы, функции и триггеры |
| [history/V1–V49](../../apps/api/src/main/resources/db/migration/history/) | Неизменённая цепочка для обновления старых БД и исторических тестов |
| Будущие `V50__…sql` и выше в корне | Следующие изменения, применимые и после B49, и после прежней V49 |

На пустой БД Flyway исполняет B49 и записывает одну выполненную миграцию типа `SQL_BASELINE`, версии 49. Исторические переносы данных, конвертации валют и backfill V1–V49 для нового старта не воспроизводятся. Приложение создаёт пользовательские профили штатными правилами.

БД с существующей историей Flyway продолжает V-цепочку; B49 к ней не применяется. Перенос SQL в `history/` сохраняет имена, версии, содержимое и checksums. Уже записанные строки `flyway_schema_history` не переписываются. Для заполненной БД без истории нельзя подменять проверку схемы включением `baselineOnMigrate` или запуском команды `baseline`: это отдельная задача принятия под управление, которую текущий механизм не выполняет.

## Следующее изменение

1. Добавьте следующий свободный `V<N>__description.sql` в корень `db/migration/`; после текущего этапа это V50. Он должен работать на результате обоих путей: исторической V49 и B49.
2. Историю V1–V49 не редактируйте. После публикации B49 также неизменяем: исправление оформляется следующей V-миграцией, чтобы свежая и существующая БД получали одинаковое изменение.
3. Проверьте пустую БД, обновление заполненной исторической БД, повторный запуск Flyway и проверку API под ограниченной runtime-ролью. Сравнивайте не только таблицы, но и ограничения, индексы, функции, триггеры и необходимые права.
4. Исторические тесты с `target` ниже 49 должны читать только `classpath:db/migration/history`. Обычный путь читает весь `classpath:db/migration`; не отключайте baseline в production ради тестовой фикстуры.

Это SQL baseline-миграция, а не ручная пометка существующей схемы командой Flyway `baseline`. Новые baseline более поздних версий требуют отдельного проверенного этапа; текущий файл не превращается в постоянно редактируемый дамп.

## Данные и эксплуатация

Наличие B49 не вызывает сброс и не является командой очистки. Обычный запуск, миграция и деплой сохраняют аккаунты, авторизацию, друзей, служебные данные и существующий игровой прогресс. Разрешённая очистка только игрового прогресса выполняется отдельной эксплуатационной процедурой с backup и проверкой сохранения данных; SQL истории и baseline для этого не редактируются.
