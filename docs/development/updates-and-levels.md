## Добавить обновление

Для выпуска web/API **0.7.0** подготовлена запись об обновлении. [Документ выпуска](../releases/release-0.7.0.md) описывает состав и порядок обновления. Для каждой новости сверяйте дату и фактически доступные игрокам изменения: публикация в Git и обновление основного сервера остаются отдельными действиями.

1. Добавьте запись в `public/updates.json → releases`. `schemaVersion` оставьте равным 1. Пример полей:

   ```json
   {
     "id": "2026-10-01-forest-update",
     "version": "0.6.6",
     "date": "2026-10-01",
     "title": "Новые возможности леса",
     "changes": ["Короткое описание видимого игроку изменения."]
   }
   ```

2. Укажите реальную версию и дату выпуска. Новые записи ставьте в начало массива; при одинаковой дате сохраняется их порядок. `id` уникален и остаётся неизменным после публикации; старые записи сохраняйте. Новое отдельное объявление получает новый ID, даже если номер версии прежний. Исправление опечатки в существующей записи не делает её непрочитанной снова.
3. Пишите о доступном игроку результате. Не копируйте коммиты, внутренние пути и результаты CI в список изменений. Не объявляйте отключённую механику работающей.
4. Проверьте `node --test tests/release-notes.test.mjs tests/beta-info.test.mjs`; перед выпуском — обычные обе сборки и тесты. Убедитесь, что `/updates.json` отдаёт JSON с новой записью из развёрнутой версии.
5. Выпустите вместе с соответствующим кодом по [инструкции эксплуатации](../operations/operations.md). Сам push или изменение `package.json` не создаёт новость на основном сервере.

Пример выше — формат, а не запланированный выпуск. Первая опубликованная запись — **0.6.5**. Запись о 0.6.3 не публикуется. Новые объявления добавляйте в начало массива, сохраняя ID уже выпущенных записей. Пустая лента `{"schemaVersion":1,"releases":[]}` тоже допустима и скрывает счётчик непрочитанного.

Формат: 0–200 записей; `id` — до 100 символов из латинских букв, цифр, `.`, `_`, `-` (начинается с буквы/цифры); `version` — до 40, `title` — до 160 символов; `changes` — 1–12 непустых пунктов до 400 символов каждый. Дата должна существовать в календаре. Текст обычный, без HTML. Некорректный файл отклоняется целиком, на экране остаётся последний корректный список.

## Как работает счётчик

- Приложение загружает `/updates.json` при запуске, возвращении во вкладку/сеть и периодически, пока вкладка видна. Открытие окна также проверяет сервер. Новость может появиться без перезагрузки страницы.
- Файл публичный, не содержит персональных данных. Он обслуживается веб-приложением; путь `/api/*` здесь не используется, поскольку на VPS его принимает Ktor.
- `fetch` использует `cache: no-store`; [next.config.ts](../../next.config.ts) и [public/_headers](../../public/_headers) задают отсутствие кеширования для двух контуров. Service Worker не перехватывает запрос новости. Встроенная копия даёт начальное содержимое и работает при недоступной сети; ошибка запроса не удаляет уже загруженный список.
- Счётчик — число записей с непрочитанными ID. При открытии окна раскрывается и отмечается последняя запись. Остальные отмечаются только при раскрытии; новая запись, пришедшая в уже открытое окно, сама прочитанной не становится.
- До восстановления прочитанных ID из хранилища счётчик не показывается: вход в игру не должен на мгновение делать все прежние новости новыми. После восстановления настоящие непрочитанные записи появляются в счётчике.
- Прочитанные ID сохраняются **для аккаунта в браузере этого устройства**, синхронизируются между вкладками. При возвращении в приложение, в том числе после восстановления замороженной страницы/PWA, прочитанное сверяется с хранилищем независимо от ограничения частоты запроса ленты. Списки объединяются, поэтому запоздавшее событие другой вкладки не отменяет просмотр.
- На другом устройстве запись может снова быть новой; серверной синхронизации прочитанного пока нет. При недоступном хранилище просмотр работает до конца сеанса. Сохранение повторяется при возвращении в приложение: если браузер снова разрешил запись, просмотр переживёт следующий запуск.
- Сама новость не перезагружает приложение и не трогает игровые данные. За автоматическую перезагрузку и техработы отвечает отдельный [механизм статуса сборки](../operations/client-updates.md). Новое объявление и новый JavaScript не зависят друг от друга.

При изменении формата сохраняйте совместимость со старыми открытыми клиентами. Ключи и политику хранения ищите в модуле записей; ID нельзя заменять индексом массива или номером последней просмотренной версии.

В `browserReleaseNotesEnvironment` браузерные таймеры вызываются через обёртки `globalThis.*`: копирование нативных методов в объект меняет их `this` и вызывает `Illegal invocation`. Обращение к браузерным API должно оставаться внутри функций, поскольку адаптер создаётся и при SSR. Регрессия в `tests/release-notes.test.mjs` проверяет контекст вызова, запуск и очистку таймеров.

## Как устроено меню уровней

Общий уровень с 0.7.2 вычисляется по постоянному опыту развития, а не по тапам. Подтверждённый сервером XP находится в `economy.progression.player.xp`. Начисления за полученную стройку, производство, освоение рецептов, добычу, исследования и завершённые заказы описаны в общем [`player-progression-catalog.json`](../../apps/api/src/main/resources/world/player-progression-catalog.json); расчёт начислений выполняют TS и Kotlin. Рендер профиля не выдаёт опыт или награды.

Всего 100 уровней, первый начинается с 0 XP. Порог уровня вычисляется из параметра каталога: `levelXpFactor × (level − 1)²`. Группы без пересечений: **1–10, 11–20, …, 91–100**. При открытии выбирается группа текущего уровня; одновременно показывается до десяти строк. Переход между группами не меняет игровой прогресс.

[`PlayerProgressionCard`](../../features/game/player-progression-card.tsx) показывает опыт внутри текущего уровня, оставшийся XP, ближайшую награду и источник последнего начисления. На 100-м уровне полоса завершена, без несуществующего следующего уровня; накопленный XP продолжает отображаться. Для вычисления доли используйте `getPlayerLevelProgress`, не `xp / nextThreshold`. Чистые helpers, таблица уровней и этапы значка находятся в [`player-levels.ts`](../../features/economy/domain/player-levels.ts), чтобы маленький значок не загружал правила начисления и весь каталог экономики.

Этапы смены значка берутся из `PLAYER_ICON_LEVELS`: **1, 10, 20, 30, 40, 50, 60, 70, 80, 90**. Замок показывает, что этап ещё не получен, но не мешает посмотреть его требования. Карточка меняет оформление на крупных рубежах. Короткая анимация проигрывается только при росте подтверждённого уровня уже открытой карточки; повторное открытие, смена аккаунта и восстановление снимка не запускают её заново. `prefers-reduced-motion` отключает движение.

Отдельная шкала «Дела леса» показывает месячный вклад за помощь жителям и корабельные грузы. Месяц меняется в **00:00 UTC**; общий XP и отношения с жителями сохраняются. Награды и их пороги берутся из того же каталога, начисляются автоматически. В подробностях видны полученные сезонные значки с месяцем получения; показаны последние 12, остальные остаются сохранены.

Тап-статистика и рейтинг остаются отдельными показателями и не определяют общий уровень. В гостевом профиле уровень берётся из `playerXp`. Подтверждённые тапы за месяц и лучший результат серии автоматически входят в таблицы друзей и мира. До получения снимка собственного опыта отображается загрузка, а не выдуманный нулевой прогресс.

Проверка UI: маленький экран, длинные числа, текущие уровни 1/10/11/70/100, повторное открытие после просмотра другой группы, клавиатура и возврат фокуса; смена месяца и сохранность сезонных значков; отсутствие повторной анимации. Тесты: [game-levels.test.mjs](../../tests/game-levels.test.mjs), [guest-profiles.test.mjs](../../tests/guest-profiles.test.mjs).
