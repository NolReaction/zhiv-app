# Мобильный эксперимент: iPhone и Android

Ветка `experiment/native-mobile` начинается от `master` [`493d399`](https://github.com/NolReaction/zhiv-app/commit/493d3990374daaa56b99a2a2524ac649556f5be2). Цель — сохранить React-интерфейс и сервер Ktor, добавив устанавливаемые приложения для iOS и Android с системными разрешениями, собственным хранением и геопозицией в фоне.

Это поэтапный эксперимент. Первый этап — отдельное диагностическое приложение `apps/mobile`, а не уже перенесённый Мохлик. Оно должно проверить работу настоящего нативного модуля на обоих телефонах до изменения входа, серверного протокола и публикации координат. Основной сайт, PWA, Sites и Next/VPS продолжают работать отдельно.

## Что входит в первый этап

- Локально собранный веб-интерфейс внутри Capacitor; проекты iOS и Android хранятся в репозитории. Приложение не загружает production-сайт через `server.url`.
- Нативная геопозиция через Capacitor Geolocation и адаптер к существующему контроллеру [`features/earth/location.ts`](../../features/earth/location.ts).
- События активности приложения через Capacitor App. В этом этапе наблюдение работает только при открытом приложении; уход в фон останавливает watch. Это сознательная граница этапа, а не фоновая геолокация.
- Простая диагностическая настройка через Capacitor Preferences. После перезапуска читается настройка; разрешение всегда проверяется у ОС отдельно.
- Возраст и точность текущего измерения видны на экране. Координаты остаются в памяти; входа в аккаунт и отправки координат на сервер нет.
- Повторные start/stop, завершение асинхронного запуска после stop, возврат из фона и ошибки разрешений не должны оставлять лишнее наблюдение.

Веб-превью показывает только интерфейс; кнопки нативной геолокации в браузере отключены. Оно не доказывает работу Core Location, Android location provider, системных разрешений или фоновых режимов.

Сборка JavaScript не означает успешную сборку iOS/Android. Наличие проектов не означает проверенную установку. Результаты каждой проверки записываются с устройством, ОС, коммитом и наблюдением; непроведённая проверка остаётся непроведённой.

## Как попробовать первый этап

Из корня репозитория:

Нужны Node.js 22.13+ (в CI — 24), для iOS — macOS и Xcode 26+, для Android — JDK 21 и SDK 36. Минимальные версии в созданных проектах: iOS 15 и Android API 24. iOS использует Swift Package Manager, CocoaPods этому стенду не нужен. [Требования Capacitor 8](https://capacitorjs.com/docs/getting-started/environment-setup).

```bash
git switch experiment/native-mobile
npm ci
npm run mobile:sync
```

`mobile:build` готовит локальный клиентский bundle. `mobile:sync` сначала выполняет эту сборку, затем переносит файлы и сведения о плагинах в оба нативных проекта. После изменения веб-кода нужно снова выполнить `mobile:sync`; одна перезагрузка приложения старый bundle не заменит.

На Mac для iPhone:

```bash
npm run mobile:ios
```

Команда открывает проект в Xcode. Выбрать подключённый iPhone, настроить свою signing team и доступный для неё bundle identifier, затем Run. Подпись и provisioning принадлежат разработчику; ключи и профили подписи не добавляются в Git. На Linux невозможно подтвердить Xcode-сборку.

Для Android:

```bash
npm run mobile:android
```

Команда открывает проект в Android Studio. Установить требуемые проектом SDK/JDK, подключить телефон с USB debugging и выполнить Run. Эмулятор полезен для интерфейса, но симулированное местоположение не подтверждает поведение GPS и батареи реального телефона.

Первый ручной проход на каждом телефоне:

1. Открыть приложение, включить «Разрешить поиск в приложении», нажать «Найти меня» и выбрать системный доступ во время использования. Проверить время измерения и точность.
2. Остановить наблюдение, снова запустить; несколько повторов не должны создавать несколько потоков обновлений.
3. Изменить диагностическую настройку, закрыть и открыть приложение. Настройка должна сохраниться; старые координаты не должны выдавать себя за новое измерение.
4. Уйти на домашний экран или заблокировать телефон. На первом этапе наблюдение должно останавливаться. После возврата проверить восстановление согласно ранее выбранному состоянию.
5. Отозвать разрешение в системных настройках, вернуться и повторить запрос. Показать реальный отказ; не подменять его сохранённым флагом «доступ разрешён».
6. Отдельно проверить приблизительное местоположение и отключённые службы геолокации. Интерфейс должен объяснять состояние без бесконечного индикатора.

## Почему нельзя сразу скопировать нынешний Next-клиент

Текущая конфигурация [`next.config.ts`](../../next.config.ts) собирает серверный `standalone`. Это не папка статического приложения, которую можно просто положить в WebView.

Перед общей мобильной сборкой требуется инвентаризация:

| Область | Текущий источник | Что сделать для мобильной сборки |
| --- | --- | --- |
| Главный экран | [`features/app/app-shell.tsx`](../../features/app/app-shell.tsx), `next/dynamic` | Использовать общие компоненты через самостоятельную клиентскую точку входа; проверить lazy imports и чанки |
| Корневые провайдеры | [`app/layout.tsx`](../../app/layout.tsx) | Перенести необходимые клиентские провайдеры в мобильную композицию; метаданные сайта оставить серверу |
| Установка и обновление | [`features/app/game-entry.tsx`](../../features/app/game-entry.tsx), [`features/pwa/`](../../features/pwa/), [`features/updates/`](../../features/updates/) | Отдельный lifecycle приложения; не запускать PWA installation gate и service-worker обновление поверх встроенного bundle |
| Навигация и изображения | Использования `next/link`, `next/navigation`, `next/image` в `features/` | Разделить переходы внутри приложения и внешние ссылки; убрать зависимость мобильного клиента от серверной оптимизации изображений |
| API и серверные обработчики | [`app/api/`](../../app/api/), [`apps/api/`](../../apps/api/), [`lib/server/`](../../lib/server/) | Оставить серверные операции на VPS; перечислить используемые endpoints, включая погодный proxy |
| Сцена, карта и звук | [`features/world/scene/map-engine.ts`](../../features/world/scene/map-engine.ts), [`features/earth/`](../../features/earth/), [`features/audio/`](../../features/audio/) | Переиспользовать код, проверить пути ресурсов, WebGL/Canvas, паузу, память, аудиосессию, safe areas и клавиатуру |

Игровые изображения, аудио и каталог переиспользуются. Смена оболочки сама по себе не исправляет ошибки рендера или синхронизации. Серверные аккаунты и прогресс остаются в Ktor/PostgreSQL; установка мобильного клиента не должна создавать новый аккаунт автоматически.

## Этап 2: транспорт и вход

Сейчас [`lib/auth-api.ts`](../../lib/auth-api.ts), [`lib/check-in-api.ts`](../../lib/check-in-api.ts) и [`features/earth/sharing-api.ts`](../../features/earth/sharing-api.ts) вызывают относительные `/api/v1/...` с `credentials: "same-origin"`. Сервер читает HttpOnly-cookie с `SameSite=Lax`; production-записи проверяют Origin в [`HttpSupport.kt`](../../apps/api/src/main/kotlin/ru/zhiv/http/HttpSupport.kt). Нативный bundle имеет другой origin. Замена относительного URL на адрес VPS не решает авторизацию.

ВК-вход в [`account-entry.tsx`](../../features/account/account-entry.tsx) заменяет текущую страницу на сайт провайдера. [`AuthRoutes.kt`](../../apps/api/src/main/kotlin/ru/zhiv/auth/AuthRoutes.kt) связывает callback с браузерной cookie и возвращает на `/`. Нельзя предполагать общую cookie между системным браузером, WebView и фоновым HTTP-клиентом.

План изменений:

1. Выделить единый интерфейс API-транспорта. Веб продолжает использовать существующий cookie-сеанс; мобильный вариант использует нативный транспорт к строго заданному HTTPS backend. Инвентаризация должна найти прямые `fetch`, загрузки и нестандартные запросы, чтобы часть клиента случайно не осталась на старом пути.
2. Добавить отдельное получение мобильного сеанса: вход в системном браузере, привязка попытки к state и PKCE, разрешённый return link, одноразовый короткоживущий код обмена. Код связан с попыткой и устройством; повтор, подмена verifier, отмена и просрочка не создают сеанс.
3. Сопоставлять мобильный сеанс с существующим пользователем и серверными правилами отзыва. Общие доменные обработчики получают проверенную идентичность через один слой авторизации. Веб-CSRF и браузерные cookie не ослабляются.
4. Долгоживущий секрет хранится в iOS Keychain; на Android — в хранилище с шифрованием ключом Android Keystore. Preferences и SQLite без дополнительной защиты не являются хранилищем токенов. Секрет не передаётся в JS, localStorage, callback URL или диагностический лог.
5. Разделить полномочия: фоновый модуль получает только необходимый доступ к текущей публикации геопозиции, без управления аккаунтом, игровыми наградами и получателями. Сервер связывает полномочия с пользователем, мобильным сеансом, сроком и действующим согласием. Полный аккаунтный токен не выдаётся произвольному плагину.
6. Нативный bridge принимает известные операции/пути и проверяет адрес назначения. Не создавать универсальный метод «отправить авторизованный запрос на любой URL». Редиректы на посторонний host не должны переносить credentials.
7. Выход и 401 останавливают наблюдение/отправку, отзывают или удаляют соответствующие credentials, очищают ожидающие координаты и блокируют поздние callbacks. Смена пользователя создаёт новое поколение состояния. Callback пользователя A не может отправиться от имени B.

Приёмка этапа включает уже существующие веб-вход, восстановление доступа, выход на других устройствах и операции аккаунта. Настройки CORS, cookie и проверки Origin не меняются ради обхода ошибок прототипа.

## Этап 4: хранение и очереди

| Данные | Целевое хранение | Правило |
| --- | --- | --- |
| Небольшие настройки интерфейса | Preferences | Версия схемы, явные значения по умолчанию, обработка ошибки чтения/записи |
| Токены и ключи | Keychain / хранилище с Keystore | Минимальные полномочия; отзыв и удаление при завершении сеанса |
| Очереди игровых команд и квитанции | SQLite | Транзакции, идентификатор владельца, поколение игры, idempotency key, явное подтверждение сервера |
| Статичные ресурсы карты/игры | Ограниченный файловый кэш | Можно восстановить; очистка кэша не удаляет аккаунт или очередь команд |
| Частная текущая GPS-точка | Память; только обоснованная краткая нативная очередь при реализации фона | Не история маршрута; только ещё допустимое последнее измерение |

Сначала ввести интерфейсы хранилищ и проверяемую миграцию, затем переводить конкретные очереди. Нельзя механически заменить синхронный localStorage на асинхронный Preferences в местах, где подтверждение записи ограждает потерю команды.

Источник текущей экономической очереди — [`features/economy/sync/use-economy.ts`](../../features/economy/sync/use-economy.ts); общая очередь игровых событий — [`features/game/game-sync-journal.ts`](../../features/game/game-sync-journal.ts). Проверки: kill между записью и отправкой, потеря ответа после server commit, повтор с тем же ключом, смена владельца, reset поколения игры, нехватка места, повреждённая запись, обновление схемы.

Старая PWA и новая установка имеют разные контейнеры данных. Серверный прогресс восстанавливается после входа. Перенос неподтверждённых локальных действий между ними требует отдельного протокола; нельзя обещать автоматический импорт из Safari/Chrome.

## Этап 5: геопозиция в фоне

Официальный Capacitor Geolocation используется для первого foreground-этапа. Фоновый сбор и отправка требуют отдельной реализации: Core Location на iOS и подходящего нативного location service на Android. На Android нужно отдельно реализовать актуальные требования к foreground service, уведомлению и разрешениям; на iOS — режим location, подходящий уровень авторизации и обработку приостановки/завершения процесса. Настройка проверяется по версиям ОС и SDK выбранной сборки.

React и WebView не являются фоновым исполнителем. Нативная часть принимает события ОС, проверяет согласие, свежесть и идентичность, отправляет точку сама и хранит лишь необходимое состояние. Экран игры может быть остановлен.

### Один владелец публикации

Сейчас [`features/earth/sharing.ts`](../../features/earth/sharing.ts) публикует только в foreground. При скрытии он прекращает публикацию и через `DELETE /location` отзывает epoch. Если добавить второй фоновый отправитель без изменения владения, веб-контроллер будет отзывать его право на отправку.

В мобильной версии lease принадлежит одному нативному контроллеру и в foreground, и в background. UI передаёт явные команды, отображает статус и не открывает параллельную публикацию. Переключение экранов не равно отзыву согласия; OFF, призрак, выход и срок доступа остаются явными причинами остановки.

Серверный контракт уже содержит необходимые ограждения в [`JdbcEarthLocationRepository.kt`](../../apps/api/src/main/kotlin/ru/zhiv/db/JdbcEarthLocationRepository.kt):

- Публикация связана с пользователем, текущим сеансом, `publicationEpoch`, режимом SHARING и сроком согласия.
- `sequence` и время измерения строго возрастают.
- Измерение принимается не старше 60 секунд и не более чем на 10 секунд из будущего.
- Успешные публикации разделяет минимум 30 секунд; это серверный предел частоты, а не обещание обновления ОС каждые 30 секунд.
- Приблизительный режим округляет точку и ограничивает точность. Клиент также округляет её до отправки.

При потере сети хранить максимум необходимое последнее измерение; старые точки отбрасывать, а не проигрывать маршрут после восстановления связи. Существующий предел свежести не увеличивается ради выгрузки очереди. Режим «последняя точка для близких» не требует журнала перемещений.

### Отзыв и приватность

- Геодоступ ОС, настройка использования геопозиции в приложении и разрешение поделиться с выбранными людьми — три разных состояния. Одно не заменяет другое.
- Фон включается отдельным понятным действием. Из старого foreground-согласия нельзя автоматически вывести согласие на постоянную отправку.
- OFF останавливает сбор, удаляет локальную ожидающую точку и применяет существующее серверное удаление. Призрак останавливает новые публикации, сохраняя предусмотренную контрактом последнюю разрешённую точку.
- Отзыв конкретного получателя, изменение точности и истечение доступа проверяются сервером при публикации. Фоновый модуль не расширяет аудиторию и не продлевает срок автоматически.
- После 401, потери lease или смены аккаунта старая очередь не повторяется с новыми credentials. Поздние асинхронные результаты ограждаются поколением владельца.
- Намеренное принудительное закрытие, экономия энергии и решения ОС могут прекратить обновления. В интерфейсе показывается реальное время последней точки; непрерывная работа после force-stop не обещается.

## Матрица приёмки на устройствах

Результаты заполняются отдельно для iPhone и Android. Для первого этапа строки о сервере и фоне имеют статус «не реализовано».

| Сценарий | Ожидаемое поведение | iPhone | Android |
| --- | --- | --- | --- |
| Чистая установка и первый явный запрос | Системный запрос разрешения, затем измерение или понятный отказ | Не проверено | Не проверено |
| Повторное открытие после разрешения | Проверяется состояние ОС, нет искусственного повторного onboarding | Не проверено | Не проверено |
| Allow once / одноразовое разрешение | После окончания разрешения повторный запрос соответствует состоянию ОС | Не проверено | Не проверено |
| Approximate / precise | Показана фактическая точность; приблизительное измерение не выдаётся за точное | Не проверено | Не проверено |
| Отказ и отзыв в настройках | Наблюдение не зависает, старый флаг не подменяет разрешение | Не проверено | Не проверено |

### Батарея и нагрузка

До выпуска сравнить на физических телефонах одинаковые интервалы: фон выключен; фон включён на месте; прогулка с погашенным экраном; плохая сеть. Записывать длительность, модель/ОС, начальный и конечный заряд, включённые режимы энергосбережения, частоту полученных/отправленных точек и диагностические данные Xcode Instruments/Android Studio. Проценты заряда за короткий интервал сами по себе ненадёжны.

Параметры точности, distance filter, пауза при неподвижности и частота отправки выбираются по измерениям. Производительность Canvas/WebGL и фоновые расходы GPS измеряются отдельно. В этой ветке пока нет подтверждённого бюджета батареи.

## Проверки и границы выпуска

13 ноября 2026, подготовка первого стенда: прошли 127 профильных JS-тестов (26 новых), TypeScript, ESLint, архитектурная проверка, mobile build/sync, Next/VPS и Sites build. Xcode project/plist разобраны, Privacy Manifest включён в ресурсы. Production dependency audit: 0 уязвимостей. Физические устройства и нативная компиляция локально не проверялись. Визуальный проход заблокирован средой: Chromium не запускается, облачный браузер не подключается к локальному preview.

Для изменения общих TypeScript-модулей выполнить `npm run typecheck`, `npm run architecture:check`, `npm run lint` и профильные тесты геопозиции/адаптера. Отдельно выполнить `npm run mobile:build` и `npm run mobile:sync`. Перед выпуском общего клиента нужны штатные Sites/Next/API-проверки из [CONTRIBUTING.md](../../CONTRIBUTING.md); команды, использующие `dist/`, запускать последовательно.

iOS-сборка, Android-сборка, установка на устройство и системные разрешения — отдельные проверки. Если среды Xcode/Android SDK или телефона нет, это ограничение фиксируется прямо. Неподписанный проект нельзя называть готовым приложением для магазина.

В [mobile.yml](../../.github/workflows/mobile.yml) добавлены Android debug APK с lint и iOS simulator build без подписи. Успешный Android job прикрепляет APK к Actions run. Это позволяет проверить компиляцию обеих платформ, но не заменяет матрицу устройств. Результат CI проверяется для конкретного коммита; наличие workflow не означает, что он уже прошёл.

Публикация в TestFlight/Google Play, настройка signing, app links, серверное развёртывание и включение фоновых полномочий — последующие этапы. Этот эксперимент не меняет production-сервер и не включает скрытый сбор геопозиции.
