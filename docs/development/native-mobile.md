# Мохлик для iPhone и Android

Мобильный клиент входит в общую кодовую базу `master`: веб/API 0.7.2 и мобильный пакет 0.3.2/build 5. У пакета отдельная версия, app ID `ru.zhiv.mochlik.lab` и имя «Мохлик · Тест». Это сборка для разработки и проверки, с отдельным контейнером данных. Наличие кода в `master` не означает публикацию в магазинах или обновление production; [состав интеграции и приёмка](../releases/native-integration.md).

## Что перенесено

Вместо диагностического экрана по умолчанию открывается настоящий общий `AppShell`: аккаунт, лес, экономика, рыбалка, карта и настройки. Лаборатория сохранена в настройках устройства и на экране входа. Интерфейс остаётся React/Canvas/WebGL внутри Capacitor WebView; сервер и подтверждённый прогресс остаются Ktor/PostgreSQL.

Разработка велась в `experiment/native-mobile` до `4c4cab6`; интеграция переносит её итог в очищенный `master` `d45316b`, сохраняя единую новость 0.7.2. Старая ветка остаётся историей разработки. В мобильном клиенте браузерные установка PWA и автообновление заменены установкой мобильного пакета; веб/PWA продолжает работать отдельно.

Собственные Android-модули находятся в `apps/mobile/android/app/src/main/kotlin/ru/zhiv/mochlik/lab`, JUnit-тесты - в `src/test/kotlin/ru/zhiv/mochlik/lab`. Новые Android-функции пишутся на Kotlin. iOS использует Swift. В 0.3.1 все 12 собственных Android-классов и прежние Java-тесты переведены на Kotlin; формат SQLite, настройки, ключ Keystore и публичные имена методов Capacitor сохранены. Удаление приложения/сброс данных для перехода не требуется; для обновления нужна та же подпись.

| Область | Реализация |
| --- | --- |
| Вход | Системный браузер, явное подтверждение существующего аккаунта, одноразовый код с S256 PKCE и state |
| Сеанс | iOS Keychain / Android AES-GCM с ключом Keystore; секрет не возвращается JavaScript |
| API | Нативный HTTP к закреплённому HTTPS origin; отдельный мобильный bearer; отмена, пределы размера, проверка владельца |
| Игровой интерфейс | Общие компоненты, самостоятельная Vite-сборка, адаптеры Next для клиентского окружения |
| Ресурсы | Игровые изображения, звук, шрифты и MapLibre включены в установку; карты и серверные данные могут требовать интернет |
| Геопозиция | Нативный поиск на карте; отдельная явно включаемая фоновая передача выбранным людям |
| Уведомления | Локальные игровые таймеры; APNs/FCM для новой почты и напоминаний об отметке, после настройки провайдеров |
| Устройство | Сеть, состояние приложения, безопасные отступы, вибрация, системное «Поделиться», внешние ссылки |
| Память и звук | Пауза при сворачивании; освобождение неиспользуемых звуковых буферов и mip-кэша рисунков по предупреждению ОС |

Оболочка не превращает React-рендер в игровой движок и не устраняет автоматически ошибки игровой логики. Нагрузку сцены, батарею и фон нужно измерять на физических устройствах.

## Перед первым входом

**Для первого входа нужен совместимый сервер с мобильным подключением и схемой V84.** У старого веб-релиза до интеграции отсутствуют `/mobile/connect` и endpoints мобильного входа. Проверяйте фактически развёрнутый SHA и схему; состояние GitHub не доказывает состояние сервера.

1. Проверить CI и резервную копию БД штатным порядком из [операционной инструкции](../operations/vps.md).
2. Развернуть совместимые web/API-компоненты. Flyway добавит V83 мобильного входа и V84 привязок APNs/FCM; старые миграции и B49 не меняются.
3. Проверить обычный веб-вход и новую страницу подключения. Мобильный токен не заменяет cookie браузера.
4. Собрать клиент для того же HTTPS backend. Для тестового сервера задать `VITE_MOBILE_API_ORIGIN` при сборке; не менять origin во время работы приложения.

Версия схемы V84 добавлена также в строгую проверку совместимости миграций и эксплуатационные инструменты. Нельзя откатывать API на старую сборку, которая не знает эту схему, без отдельно проверенного плана отката.

## Сборка и установка

Нужны Node.js 22.13+ (CI: 24); для iOS - Mac и Xcode 26+, для Android - JDK 21 и SDK 36. Проекты рассчитаны на iOS 15+ и Android API 24+. Существующий Ktor API собирается JDK 25.

Android-сборка закрепляет Kotlin 2.3.21, AGP 8.13.2 и Gradle 8.14.3. Цель Kotlin JVM 21 совпадает с Java-целью подключённых модулей Capacitor. AGP обновлён в пределах 8.13 для поддержки Kotlin 2.3; сгенерированные `capacitor.*.gradle` не редактируются вручную. При обновлении версий сверять [матрицу Kotlin/Gradle/AGP](https://kotlinlang.org/docs/gradle-configure-project.html) и [поддержку Kotlin 2.3 в AGP 8.13.2](https://developer.android.com/build/releases/agp-8-13-0-release-notes).

Из корня репозитория:

```bash
git clone https://github.com/NolReaction/zhiv-app.git zhiv-app-mobile
cd zhiv-app-mobile
npm ci
npm run mobile:sync
```

Этот пример создаёт новый каталог с актуальным `master`; существующий checkout и его настройки Xcode сохраняются. После очистки истории старый локальный `master` может расходиться с удалённым: не объединяйте их обычным merge. Для последующих обновлений уже согласованного checkout используйте `git pull --ff-only origin master`. Локальные изменения signing team в Xcode нужно сохранить; не применять `reset --hard` ради обновления проекта.

Если `pull` остановился на `apps/mobile/ios/App/App.xcodeproj/project.pbxproj`, сначала закрыть Xcode и посмотреть `git diff -- apps/mobile/ios/App/App.xcodeproj/project.pbxproj`. Если изменения ограничены своей Team и переупорядочиванием/форматированием настроек Xcode, сохранить именно этот файл перед повторным обновлением:

```bash
git stash push -m "xcode-signing-before-update" -- apps/mobile/ios/App/App.xcodeproj/project.pbxproj &&
git pull --ff-only origin master
```

Затем продолжить с `npm ci` и `npm run mobile:sync`. После открытия Xcode повторно выбрать прежнюю Team, оставить bundle ID `ru.zhiv.mochlik.lab` и установить поверх прежнего приложения. Stash остаётся резервной копией; автоматически выполнять `stash pop` не нужно: старый файл проекта может конфликтовать с новой версией. Другие собственные изменения требуют отдельного разбора diff.

```bash
npm run mobile:ios
# либо
npm run mobile:android
```

В Xcode выбрать подключённый iPhone, свою Team и Run. В Android Studio выбрать телефон с USB debugging и Run. Бесплатная/платная подпись и аккаунты магазинов принадлежат разработчику; ключи не добавляются в Git.

`mobile:build` сначала проверяет совпадение версии/номера сборки/app ID в JS, iOS и Android, закрепляет backend в нативной конфигурации, затем собирает интерфейс и ресурсы. `mobile:sync` обновляет обе платформы и плагины. После изменения TS/React нужно повторить sync и собрать приложение. Запуск `mobile:dev` показывает только пояснение: без нативных плагинов полноценный клиент не имитируется.

Настройки сборки читаются из корневых `.env*` и переменных процесса:

```bash
VITE_MOBILE_API_ORIGIN=https://your-test-host.example npm run mobile:sync
```

По умолчанию origin - `https://im-alive.ru`. Для внешних карт используется тот же публичный `NEXT_PUBLIC_MAPTILER_KEY`, что и в веб-сборке. URL должен быть HTTPS origin без пути, query, пароля и fragment. Изменение сервера отделяет сохранённый сеанс от прежнего backend.

## Вход и границы доверия

Нативная часть генерирует verifier и state; открывает `/mobile/connect?challenge=...&state=...&platform=...` в системном браузере. На сайте пользователь входит привычным способом и явно подтверждает имя аккаунта. Сервер выдаёт код, действующий две минуты и связанный с исходным браузерным сеансом, платформой, state и challenge. Код одноразовый; обмен происходит только в нативном HTTP-клиенте.

Callback фиксирован: `ru.zhiv.mochlik.lab://auth/callback`. Произвольные redirect URL не принимаются. Потерянный ответ после обмена может потребовать повторного входа; повторно использовать код нельзя. ВК/почта, привязка способов входа, восстановление и операции с доказательством владения выполняются в браузере. Обычные игровые запросы и просмотр аккаунта идут через мобильный сеанс.

Общий [`apiFetch`](../../lib/api-fetch.ts) сохраняет обычный fetch для веба. Нативный transport допускает только `/api/v1/`, не позволяет JavaScript вызывать выдачу токенов, не отправляет браузерные cookies и не следует редиректам. Пределы: 6 МиБ запроса, 16 МиБ ответа, 30 секунд. Тело передаётся байтами; JSON и multipart не повреждаются перекодированием.

`sessionChange` немедленно скрывает прежний аккаунт. Следующий мир монтируется после последовательного восстановления его данных. До и после асинхронных операций проверяются владелец и поколение сеанса; поздний ответ аккаунта A не применяется к B. Logout удаляет локальный доступ сразу; серверный отзыв при отсутствии сети может не завершиться, поэтому удалённый сеанс при необходимости отзывается с другого устройства.

Инвариант сервера: действующий токен не переназначается другому UUID. Объединение сохраняет аккаунт инициатора, отзывает остальные сессии обоих аккаунтов; восстановление создаёт новую сессию. Нативный клиент узнаёт об отзыве по 401. Его проверки владельца опираются на этот порядок: будущие операции переноса аккаунтов должны отзывать и перевыпускать сеансы, а не менять владельца действующего токена.

## Хранение: точное покрытие

| Данные | Текущее хранение |
| --- | --- |
| Секрет мобильного сеанса | Keychain / Keystore, только нативный код |
| Звук, подсказки нажатий, атлас и обучение рыбалке | Preferences, загрузка перед монтированием, последовательные записи с состоянием ошибки |
| Передаваемые идемпотентные экономические команды | SQLite: транзакция до сети, исходный requestId, владелец и поколение, восстановление через существующую reconciliation |
| Непереданное производство, подготовленные забросы, результат и текущая попытка рыбалки | SQLite: асинхронная запись до принятия действия; восстановление точной команды/попытки |
| Нажатия и их последовательность | SQLite: сначала commit, затем видимые итоги и возможность отправки |
| Неподтверждённые действия мира, получение наград и отметка | SQLite: исходный идентификатор, запрет нового действия при неопределённом результате записи |
| Выбор геопозиции и ожидающий OFF/призрак | SQLite с владельцем; остановка поиска/передачи немедленная, включение ждёт сохранения; отдельный выбор фона хранится нативно |
| Подтверждённый игровой прогресс | PostgreSQL на сервере |
| Текущая GPS-точка | Только необходимое текущее измерение, без истории маршрута |

SQLite-квитанция удаляется только после подходящего ответа; потерянный ответ оставляет исходную команду для безопасного повторения. Смена аккаунта и reset поколения не пересылают старую очередь новым владельцем. Подробности и ограничения: [native-storage/README.md](../../apps/mobile/src/native-storage/README.md).

У PWA и установленного клиента разные контейнеры. Серверный прогресс восстанавливается после входа; автоматического импорта неподтверждённых действий из Safari/Chrome нет. Небольшие UI-черновики, кэши и повторно загружаемые серверные снимки могут оставаться в WebView; они не подменяют долговечный журнал действий. Обновление SQLite с версии 1 до 2 сохраняет уже накопленные квитанции. Неопределённый результат записи останавливает принятие новых действий до повторного чтения базы при запуске.

## Геопозиция и фон

При первом поиске нужен тап «Найти меня» и системное разрешение. С версии 0.3.2 при входе на карту координаты определяются автоматически, если разрешение ОС уже выдано, геопозиция включена и призрак выключен. Автоматический запрос повторно проверяет разрешение перед регистрацией watch и никогда не открывает системный диалог. Отказ, уход с карты, OFF, призрак и смена аккаунта отменяют ожидающий запуск. Частная точка появляется без принудительного перемещения камеры.

Сохранённый ACTIVE при холодном запуске по-прежнему становится READY: старый watch не восстанавливается при загрузке приложения. Вход на карту с подтверждённым разрешением запускает новый поиск после подтверждения записи SQLite. Ошибка записи не включает поиск. Разрешение ОС не выбирает получателей; ранее включённый обмен возобновляется только в пределах сохранённых правил доступа. Переключатель «Обновлять в фоне» доступен в панели «Геопозиция» на карте и в профиле, по умолчанию выключен. Он не меняет получателей или срок доступа; выключение доступно даже при выключенном основном переключателе геопозиции.

Передачей в мобильном клиенте управляет один нативный publisher и в foreground, и в background. React не отправляет конкурирующие точки и не отзывает его lease только из-за скрытия экрана, когда фон явно разрешён. Перед отправкой нативный код проверяет текущие серверные правила и срок согласия. OFF, призрак, выход, смена аккаунта, 401/409 и потеря epoch останавливают соответствующую публикацию.

iOS использует Core Location, режим location и системный индикатор. Android использует location foreground service, запускаемый из видимого приложения, с постоянным системным уведомлением. Автоматического запуска после перезагрузки или смерти процесса нет; `ACCESS_BACKGROUND_LOCATION` не запрашивается. Повторный запуск и автоматическое восстановление не показывают диалог разрешения без явного действия.

Сохраняются серверные ограничения: измерение не старше 60 секунд, не более 10 секунд из будущего, возрастающие sequence и время, публикации не чаще одного раза в 30 секунд. Это **не обещание** получения GPS каждые 30 секунд. При потере сети старый маршрут не выгружается. Принудительное закрытие и решения ОС могут остановить работу; на экране нужно ориентироваться на фактическое время последнего измерения.

## Уведомления, память и устройство

Локальные напоминания включаются отдельно пользователем с разрешением ОС; ключи APNs/FCM для них не нужны. Они планируются по подтверждённому состоянию экономики с поправкой времени сервера. Учитываются настройки, тихие часы, суточные ограничения и владелец; в очереди не более 32 уведомлений. Смена аккаунта/выход отменяет старые напоминания, переход по уведомлению проверяет владельца. После действий с другого устройства расписание актуализируется при следующей синхронизации. ОС Android может задержать доставку.

Серверный APNs/FCM-контур доставляет новую административную почту и напоминания об отметке. Он использует общие настройки, тихие часы, дневной бюджет и очередь; игровые таймеры остаются локальными. Регистрация устройства привязана к живому мобильному сеансу, платформе и владельцу. Android data-only сообщение проверяется службой перед показом; iOS получает общий текст без содержимого письма/координат, переход всегда проверяет владельца.

По умолчанию remote push выключен. Нужны ключи Apple/Firebase на API и настройка подписанной сборки; интерфейс не запрашивает это разрешение, пока конфигурация недоступна. Сеанс, выданный до V84, требует одного нового входа. Точные переменные, Xcode/Firebase, ограничения offline logout и приёмка: [native-push.md](../operations/native-push.md). Это реализация доставки, но не свидетельство реальной отправки на телефон: реальные провайдеры в разработке не подключались.

Сворачивание приостанавливает звук/рендер и вызывает сохранение ожидающих настроек. Предупреждение о памяти освобождает неиспользуемые декодированные звуки и mip-кэш изображений; активные звуковые буферы не уничтожаются. Исходные картинки/звук входят в приложение, а не заново скачиваются с сайта. Это не делает объём памяти JavaScript неограниченным.

С версии 0.3.2 фон страницы и карты доходит до краёв экрана без непрозрачной статусной подложки и обрезания прокрутки над home indicator. Кнопки и последняя карточка сохраняют безопасные отступы. `SystemBars` задаёт светлые системные значки. На Android сначала используются CSS-insets Capacitor: они учитывают padding, уже добавленный старыми WebView, и не удваивают отступы. На iOS используются `env(safe-area-inset-*)` с нативным резервным значением. Вибрация и системное меню «Поделиться» используют нативные плагины. Внешние HTTPS-ссылки открываются в браузере, а не заменяют доверенный документ с bridge.

## Обновления установленного приложения

Игровой JavaScript и история `updates.json` входят в установленную сборку. Деплой сайта не обновляет этот пакет: нужна новая установка через Xcode/Android Studio либо будущий канал распространения. Экран новостей показывает историю установленной версии, не обещает загрузить новую мобильную версию.

Мобильный вход монтирует AppShell напрямую; браузерные InstallationGate, AppLifecycle и service worker не запускаются. Дополнительные проверки платформы запрещают старт web-updater/SW даже при случайном повторном подключении этих компонентов. `app-status.json`, `sw.js` и страницы `recover.*` в пакет не включаются. Web-механизм maintenance/reload не опрашивается; ошибки API обрабатываются существующими игровыми экранами.

При ошибке запуска доступна диагностика устройства вместо перехода на отсутствующую `/recover.html`. Явный перезапуск после ошибки или подтверждённого сброса игрового поколения загружает ту же установленную сборку; это не обновление версии и не очистка пользовательских данных.

Сбор данных и required reason APIs отражены в [инвентаризации privacy manifest](native-mobile-privacy.md). Manifest полного клиента отличается от первого лабораторного стенда без аккаунта и передачи координат.

## Проверки и приёмка

Пользователь проверил первый стенд на iPhone: разрешение, координаты, повторный запуск; затем прислал рабочие экраны полного клиента (главная, профиль, карта и собственная точка). Это подтверждает основной запуск, но не заменяет приёмку 0.3.2 и длительного фонового режима. На текущем этапе выполнены профильные JS-тесты транспорта, владельцев, SQLite-восстановления, уведомлений, lifecycle и общих браузерных контрактов; результаты полной сборки фиксируются в `WORK_STATE.md` и [PR №41](https://github.com/NolReaction/zhiv-app/pull/41).

GitHub Actions собирает Android APK, запускает lint/JUnit и проверяет итоговый merged manifest push-службы; собирает iOS для симулятора и iPhone без подписи, запускает исполняемые Swift-проверки URL-политики. `NativeBridgeContractTest` проверяет публичные JVM-сигнатуры и имена методов/плагинов, доступность конструкторов компонентов Android и reflection callback разрешения геопозиции после перевода на Kotlin. Отдельно проверяются Ktor/PostgreSQL, Sites, Next/VPS и production Compose. Добавлена браузерная проверка `npm run test:mobile-layout`: реальные стили мобильной сборки, навигация и настройки на 320/440 px, в landscape и при обоих способах применения Android-insets. Проверяются края контента, вырезы, нижняя панель, отсутствие горизонтальной прокрутки и доступность последнего элемента. В CI используются Playwright 1.62.1 и Chromium 151 с CDP-подменой safe-area env(); `BROWSER_EXECUTABLE_PATH` задаёт браузер, `PLAYWRIGHT_NODE_MODULES` - внешнюю установку Playwright. CI сохраняет снимки экрана. Это проверка геометрии с заданными insets, не эмуляция iOS. Наличие workflow не равно его успешному завершению.

На **обоих физических телефонах** нужны:

1. Чистая установка, существующий аккаунт, отмена/повтор входа, полный перезапуск, выход и другой аккаунт.
2. Открытие леса, рыбалки и карты; настоящее действие и совпадение прогресса в вебе.
3. Обрыв сети до/после серверного подтверждения; повторное открытие без дублирования наград.
4. Первое разрешение, автоматическая точка при повторном входе на карту и после перезапуска; отказ/отзыв без повторяющегося диалога, OFF/призрак, точное/примерное положение, выключенные службы.
5. Фон с заблокированным экраном, OFF/призрак, истечение доступа, выход и отзыв с другого устройства.
6. Разрешение/отказ локальных уведомлений, завершение/отмена задания, тихие часы, нажатие после смены аккаунта. После настройки APNs/FCM отдельно проверить новую почту и напоминание об отметке, холодный запуск по tap, ротацию токена, отзыв и offline logout.
7. Часы/Dynamic Island/системные панели, поворот, клавиатура, ссылки, жесты, звук/беззвучный режим.
8. Прогулка и неподвижность с погашенным экраном; измерение батареи, памяти и температуры.

Локальная web-сборка не заменяет эти испытания. Публикация TestFlight/Google Play и настройка production-сервиса - отдельные действия.
