# Мохлик для iPhone и Android

Ветка `experiment/native-mobile` от `master` `493d399`. Мобильный клиент 0.2.0, app ID `ru.zhiv.mochlik.lab`, имя «Мохлик · Тест». Это тестовая установка с отдельным контейнером данных. В `master` изменения не влиты; production в рамках разработки не развёртывался.

## Что перенесено

Вместо диагностического экрана по умолчанию открывается настоящий общий `AppShell`: аккаунт, лес, экономика, рыбалка, карта и настройки. Лаборатория сохранена в настройках устройства и на экране входа. Интерфейс остаётся React/Canvas/WebGL внутри Capacitor WebView; сервер и подтверждённый прогресс остаются Ktor/PostgreSQL.

| Область | Реализация |
| --- | --- |
| Вход | Системный браузер, явное подтверждение существующего аккаунта, одноразовый код с S256 PKCE и state |
| Сеанс | iOS Keychain / Android AES-GCM с ключом Keystore; секрет не возвращается JavaScript |
| API | Нативный HTTP к закреплённому HTTPS origin; отдельный мобильный bearer; отмена, пределы размера, проверка владельца |
| Игровой интерфейс | Общие компоненты, самостоятельная Vite-сборка, адаптеры Next для клиентского окружения |
| Ресурсы | Игровые изображения, звук, шрифты и MapLibre включены в установку; карты и серверные данные могут требовать интернет |
| Геопозиция | Нативный поиск на карте; отдельная явно включаемая фоновая передача выбранным людям |
| Уведомления | Системные локальные напоминания о строительстве, производстве и возвращении из вылазки |
| Устройство | Сеть, состояние приложения, безопасные отступы, вибрация, системное «Поделиться», внешние ссылки |
| Память и звук | Пауза при сворачивании; освобождение неиспользуемых звуковых буферов и mip-кэша рисунков по предупреждению ОС |

Оболочка не превращает React-рендер в игровой движок и не устраняет автоматически ошибки игровой логики. Нагрузку сцены, батарею и фон нужно измерять на физических устройствах.

## Перед первым входом

**Одной установки новой сборки недостаточно: серверу нужны web и API из этой же ветки.** На прежнем production отсутствуют страница `/mobile/connect` и endpoints мобильного подключения.

1. Проверить CI и резервную копию БД штатным порядком из [операционной инструкции](../operations/vps.md).
2. Развернуть совместимые web/API-компоненты. Flyway добавит `V83__mobile_authorization_codes.sql`; старые миграции и B49 не меняются.
3. Проверить обычный веб-вход и новую страницу подключения. Мобильный токен не заменяет cookie браузера.
4. Собрать клиент для того же HTTPS backend. Для тестового сервера задать `VITE_MOBILE_API_ORIGIN` при сборке; не менять origin во время работы приложения.

Версия схемы V83 добавлена также в строгую проверку совместимости миграций и эксплуатационные инструменты. Нельзя откатывать API на старую сборку, которая не знает эту схему, без отдельно проверенного плана отката.

## Сборка и установка

Нужны Node.js 22.13+ (CI: 24); для iOS — Mac и Xcode 26+, для Android — JDK 21 и SDK 36. Проекты рассчитаны на iOS 15+ и Android API 24+. Существующий Ktor API собирается JDK 25.

Из корня репозитория:

```bash
git fetch origin
git switch experiment/native-mobile
git pull --ff-only
npm ci
npm run mobile:sync
```

Локальные изменения signing team в Xcode нужно сохранить при обновлении Git. Не применять `reset --hard` ради обновления проекта.

```bash
npm run mobile:ios
# либо
npm run mobile:android
```

В Xcode выбрать подключённый iPhone, свою Team и Run. В Android Studio выбрать телефон с USB debugging и Run. Бесплатная/платная подпись и аккаунты магазинов принадлежат разработчику; ключи не добавляются в Git.

`mobile:build` сначала закрепляет backend в нативной конфигурации, затем собирает интерфейс и ресурсы. `mobile:sync` обновляет обе платформы и плагины. После изменения TS/React нужно повторить sync и собрать приложение. Запуск `mobile:dev` показывает только пояснение: без нативных плагинов полноценный клиент не имитируется.

Настройки сборки читаются из корневых `.env*` и переменных процесса:

```bash
VITE_MOBILE_API_ORIGIN=https://your-test-host.example npm run mobile:sync
```

По умолчанию origin — `https://im-alive.ru`. Для внешних карт используется тот же публичный `NEXT_PUBLIC_MAPTILER_KEY`, что и в веб-сборке. URL должен быть HTTPS origin без пути, query, пароля и fragment. Изменение сервера отделяет сохранённый сеанс от прежнего backend.

## Вход и границы доверия

Нативная часть генерирует verifier и state; открывает `/mobile/connect?challenge=...&state=...&platform=...` в системном браузере. На сайте пользователь входит привычным способом и явно подтверждает имя аккаунта. Сервер выдаёт код, действующий две минуты и связанный с исходным браузерным сеансом, платформой, state и challenge. Код одноразовый; обмен происходит только в нативном HTTP-клиенте.

Callback фиксирован: `ru.zhiv.mochlik.lab://auth/callback`. Произвольные redirect URL не принимаются. Потерянный ответ после обмена может потребовать повторного входа; повторно использовать код нельзя. ВК/почта, привязка способов входа, восстановление и операции с доказательством владения выполняются в браузере. Обычные игровые запросы и просмотр аккаунта идут через мобильный сеанс.

Общий [`apiFetch`](../../lib/api-fetch.ts) сохраняет обычный fetch для веба. Нативный transport допускает только `/api/v1/`, не позволяет JavaScript вызывать выдачу токенов, не отправляет браузерные cookies и не следует редиректам. Пределы: 6 МиБ запроса, 16 МиБ ответа, 30 секунд. Тело передаётся байтами; JSON и multipart не повреждаются перекодированием.

`sessionChange` немедленно скрывает прежний аккаунт. Следующий мир монтируется после последовательного восстановления его данных. До и после асинхронных операций проверяются владелец и поколение сеанса; поздний ответ аккаунта A не применяется к B. Logout удаляет локальный доступ сразу; серверный отзыв при отсутствии сети может не завершиться, поэтому удалённый сеанс при необходимости отзывается с другого устройства.

Инвариант сервера: действующий токен не переназначается другому UUID. Объединение сохраняет аккаунт инициатора, отзывает остальные сессии обоих аккаунтов; восстановление создаёт новую сессию. Нативный клиент узнаёт об отзыве по 401. Его проверки владельца опираются на этот порядок: будущие операции переноса аккаунтов должны отзывать и перевыпускать сеансы, а не менять владельца действующего токена.

## Хранение: точное покрытие

| Данные | Текущее хранение |
| --- | --- |
| Секрет мобильного сеанса | Keychain / Keystore, только нативный код |
| Звук, подсказки нажатий, атлас и обучение рыбалке | Preferences, загрузка перед монтированием, последовательные записи с состоянием ошибки |
| Передаваемые идемпотентные экономические команды | SQLite: транзакция до сети, исходный requestId, владелец и поколение, восстановление через существующую reconciliation |
| Непереданные производственные действия, подготовленные забросы, журнал нажатий | Существующие синхронные журналы WebView; их контракт не подменён асинхронной имитацией |
| Выбор геосогласия в интерфейсе | Существующий синхронный контракт; отдельный выбор фона хранится нативно для аккаунта |
| Подтверждённый игровой прогресс | PostgreSQL на сервере |
| Текущая GPS-точка | Только необходимое текущее измерение, без истории маршрута |

SQLite-квитанция удаляется только после подходящего ответа; потерянный ответ оставляет исходную команду для безопасного повторения. Смена аккаунта и reset поколения не пересылают старую очередь новым владельцем. Подробности и ограничения: [native-storage/README.md](../../apps/mobile/src/native-storage/README.md).

У PWA и установленного клиента разные контейнеры. Серверный прогресс восстанавливается после входа; автоматического импорта неподтверждённых действий из Safari/Chrome нет. Все клиентские данные пока не перенесены в SQLite.

## Геопозиция и фон

Поиск своего положения и передача другим — разные действия. Разрешение ОС не включает передачу и не выбирает получателей. В профиле добавлен отдельный переключатель фоновой передачи; по умолчанию она выключена.

Передачей в мобильном клиенте управляет один нативный publisher и в foreground, и в background. React не отправляет конкурирующие точки и не отзывает его lease только из-за скрытия экрана, когда фон явно разрешён. Перед отправкой нативный код проверяет текущие серверные правила и срок согласия. OFF, призрак, выход, смена аккаунта, 401/409 и потеря epoch останавливают соответствующую публикацию.

iOS использует Core Location, режим location и системный индикатор. Android использует location foreground service, запускаемый из видимого приложения, с постоянным системным уведомлением. Автоматического запуска после перезагрузки или смерти процесса нет; `ACCESS_BACKGROUND_LOCATION` не запрашивается. Повторный запуск и автоматическое восстановление не показывают диалог разрешения без явного действия.

Сохраняются серверные ограничения: измерение не старше 60 секунд, не более 10 секунд из будущего, возрастающие sequence и время, публикации не чаще одного раза в 30 секунд. Это **не обещание** получения GPS каждые 30 секунд. При потере сети старый маршрут не выгружается. Принудительное закрытие и решения ОС могут остановить работу; на экране нужно ориентироваться на фактическое время последнего измерения.

## Уведомления, память и устройство

Локальные напоминания планируются по подтверждённому состоянию экономики с поправкой времени сервера. Учитываются настройки, тихие часы, суточные ограничения и владелец; в очереди не более 32 уведомлений. Смена аккаунта/выход отменяет старые напоминания, переход по уведомлению проверяет владельца. После действий с другого устройства расписание актуализируется при следующей синхронизации. ОС Android может задержать доставку.

Это не серверный APNs/FCM push: уведомления о входящих событиях от других игроков, административной почте и отметках не доставляются через мобильную push-инфраструктуру. Для неё нужны отдельные регистрация устройств, серверная доставка и конфигурация Apple/Firebase. Интерфейс не предлагает недоступные темы как работающие.

Сворачивание приостанавливает звук/рендер и вызывает сохранение ожидающих настроек. Предупреждение о памяти освобождает неиспользуемые декодированные звуки и mip-кэш изображений; активные звуковые буферы не уничтожаются. Исходные картинки/звук входят в приложение, а не заново скачиваются с сайта. Это не делает объём памяти JavaScript неограниченным.

Безопасные отступы приходят из нативных window insets и применяются в общей CSS. Вибрация и системное меню «Поделиться» используют нативные плагины. Внешние HTTPS-ссылки открываются в браузере, а не заменяют доверенный документ с bridge.

## Обновления установленного приложения

Игровой JavaScript и история `updates.json` входят в установленную сборку. Деплой сайта не обновляет этот пакет: нужна новая установка через Xcode/Android Studio либо будущий канал распространения. Экран новостей показывает историю установленной версии, не обещает загрузить новую мобильную версию.

Мобильный вход монтирует AppShell напрямую; браузерные InstallationGate, AppLifecycle и service worker не запускаются. Дополнительные проверки платформы запрещают старт web-updater/SW даже при случайном повторном подключении этих компонентов. `app-status.json`, `sw.js` и страницы `recover.*` в пакет не включаются. Web-механизм maintenance/reload не опрашивается; ошибки API обрабатываются существующими игровыми экранами.

При ошибке запуска доступна диагностика устройства вместо перехода на отсутствующую `/recover.html`. Явный перезапуск после ошибки или подтверждённого сброса игрового поколения загружает ту же установленную сборку; это не обновление версии и не очистка пользовательских данных.

Сбор данных и required reason APIs отражены в [инвентаризации privacy manifest](native-mobile-privacy.md). Manifest полного клиента отличается от первого лабораторного стенда без аккаунта и передачи координат.

## Проверки и приёмка

Первый стенд проверен пользователем на iPhone: системное разрешение, получение координат, повторный запуск. Это не проверка новой полной версии и не проверка длительного фонового режима. На текущем этапе выполнены профильные JS-тесты транспорта, владельцев, SQLite-восстановления, уведомлений, lifecycle и общих браузерных контрактов; результаты полной сборки фиксируются в `WORK_STATE.md` и [PR №41](https://github.com/NolReaction/zhiv-app/pull/41).

GitHub Actions собирает Android APK, запускает lint/JUnit; собирает iOS для симулятора без подписи и компилирует исполняемые Swift-проверки URL-политики. Отдельно проверяются Ktor/PostgreSQL, Sites, Next/VPS и production Compose. Наличие workflow не равно его успешному завершению.

На **обоих физических телефонах** нужны:

1. Чистая установка, существующий аккаунт, отмена/повтор входа, полный перезапуск, выход и другой аккаунт.
2. Открытие леса, рыбалки и карты; настоящее действие и совпадение прогресса в вебе.
3. Обрыв сети до/после серверного подтверждения; повторное открытие без дублирования наград.
4. Разрешение/отказ/отзыв геопозиции, точное/примерное положение, выключенные службы.
5. Фон с заблокированным экраном, OFF/призрак, истечение доступа, выход и отзыв с другого устройства.
6. Разрешение/отказ уведомлений, завершение/отмена задания, тихие часы, нажатие после смены аккаунта.
7. Часы/Dynamic Island/системные панели, поворот, клавиатура, ссылки, жесты, звук/беззвучный режим.
8. Прогулка и неподвижность с погашенным экраном; измерение батареи, памяти и температуры.

Локальная web-сборка не заменяет эти испытания. Публикация TestFlight/Google Play и настройка production-сервиса — отдельные действия.
